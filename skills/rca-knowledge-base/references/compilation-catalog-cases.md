# Domain: Compilation — case catalog by error signature (reference)

Open this file **only from `compilation.md`'s Verify step 7**, after you have already classified the
outcome and identified the actual `IsWarning: false` error(s) (or a pasted signature) — never before, and
never as a way to "look for something recognizable" before finishing that partition. Recognizing an entry
below is not evidence that it is the blocking error; it only tells you what a signature you *already
confirmed via `IsWarning`* likely means and how to fix it.

**Not what you're looking for?** If the error doesn't match anything below, or you have no error at all
(a pure advisory/consultation question), see `compilation-catalog-reference.md` instead — generic
`CS####` fallback tables and expected-behavior topics live there, not in this file.

Real-world compilation cases, by category: stale/generated metadata,
custom code & packaging, UI/timeouts & post-compile behavior, permissions & file system, server
environment. Every entry is tagged by **evidence tier**:

- **`[Tier A]`** — fully diagnosable from a platform read; commit to the diagnosis. Includes cases where
  the error text itself is self-contained and unambiguous (e.g. a `CS####` message that names its own
  fix) — the "platform read" is simply reading that text via `CompilationHistory`, and no outside context
  is needed to act on it.
- **`[Tier B]`** — recognized by signature with partial on-platform corroboration; say plainly what's
  confirmed and what isn't. This is also where a case needs a fact you have but a platform read can't
  confirm (e.g. "this environment is on .NET 6+/Linux") — the signature alone isn't self-contained the way
  Tier A is.
- **`[Tier C]`** — the evidence lives off-platform (server, file system, browser); recognize the
  signature, give the known fix, and say clearly this cannot be verified from here. **Escalate to
  infra/support when the fix needs access you don't have** — some Tier C fixes are entirely in the
  requester's own hands (e.g. a local dev container's restart policy), where no escalation is needed at
  all; don't force one on habit.

**Some entries have a *delivery variant*, and it is not optional context.** A build that ran as a stage of
a package or application installation produces the same error codes as one someone started by hand, and the
fix is frequently the opposite: on the source environment and its archive rather than on the environment in
front of you. Where an entry carries a *Delivery variant*, read it whenever the build had a delivery behind
it, and read the stand-alone text otherwise. The question of **whether the delivery caused the failure at
all** is not settled here — `installation.md` §5.2 owns that gate, and a delivery-context entry is
matched only after it has returned its verdict. Never conclude "the install broke it" from the fact that an
entry below has a delivery variant.

How to use this: match the error signature (from `CompilationHistory.ErrorsWarnings`, the log
`Description`, or text the user pasted) to an entry below, then follow **that entry's own tier
discipline** (see the legend above). No entry here requires a write — if a fix needs a change, it is
always a manual step for a human. Entries that don't match anything below fall back to
`compilation-catalog-reference.md` §1.

## 1. Stale/generated code & metadata

**C1 — Stale/incomplete generated code (`CS0234`/`CS0246`, or "Index was outside the bounds of the array")** `[Tier A]`
- *Signature:* `CS0234`/`CS0246` on a type/namespace the user says they never touched, or an "Index was
  outside the bounds of the array" error — often right after a schema change, an app/package deletion, or
  an interrupted source-code generation. Errors inside `*.BackReferences.cs` are a strong tell.
- *Verify:* confirm via `CompilationHistory` that the named type/namespace has no genuine custom edit
  behind it, and that the error sits in autogenerated code. Optional bonus check: `SysSchema.LastError`
  for the named schema (see `rca-env-readonly-query`) can hold a corroborating stored error message.
- *Recommendation:* regenerate — "Generate source code for all schemas", then "Compile all". This clears
  the large majority of these. If regeneration doesn't help, it's a deeper cause (a genuinely missing
  library — **C8**; a csproj defect — **C12**/**C17**; or a post-upgrade defect — **C3**) — say so rather
  than repeating the same advice.

**C2 — Invalid Source Code Schema (SCS) cascade across linked objects** `[Tier A]`
- *Signature:* dozens of compilation errors across objects that all reference one custom object; the
  errors point at *generated* schemas of linked objects, not hand-written code.
- *Verify:* order the `CompilationHistory` errors and identify the root object per `rca-root-cause-vs-consequence`
  — the rest reference it. Optional bonus check: `SysSchema.LastError` for that root schema (see
  `rca-env-readonly-query`) for a corroborating stored error message.
- *Recommendation:* regenerate source code for the root object and recompile. If the SCS is corrupted
  beyond regeneration, restoring the schema (or, worst case, the site) from a backup/source environment is
  a human/admin decision — describe it as a recommendation, do not attempt it.

**C3 — `CS0234` persists after an 8.3.x upgrade (regeneration doesn't fix it)** `[Tier B]`
- *Signature:* `CS0234` in custom packages appearing right after an upgrade (e.g. to 8.3.3) that does
  **not** clear after a full "Generate source code for all" + "Compile all" — the standard **C1** recipe
  fails.
- *Verify:* confirm via `CompilationHistory` that the error persists after a *fresh* full compile (a
  timestamp after the last regeneration attempt). Whether this specific upgrade path is a known product
  defect is not something a platform read can confirm — that part is signature recognition, not a
  verified fact.
- *Recommendation:* re-export the affected custom packages from the source/dev environment and reinstall
  them on the upgraded environment, then compile. Flag this as a known post-upgrade pattern distinct from
  C1; if reinstalling isn't possible, recommend escalating with the compilation logs.

**C4 — A vendor package shipped uncompiled (e.g. `CrtCloudIntegration`)** `[Tier A]`
- *Signature:* errors inside an OOTB package the user says they never touched — missing class definitions
  in its autogenerated schemas (a pattern like "Cannot implicitly convert type '...EventsProcess' to
  '...EmbeddedProcess'"), sometimes reported on more than one site of the same release.
- *Verify:* read `CompilationHistory` for the error naming the vendor package's own schema; corroborate by
  resolving the package's `UId` from `SysPackage.Name` and checking `PackageCompilationState.NeedCompile`/
  `NeedCompileOData` for that `PackageUId` (see `rca-env-readonly-query`).
- *Recommendation:* compile the named package explicitly (a package-level compile) — this typically clears
  it from both full compilation and script-task publishing. Frame it to the user as a likely vendor-side
  release defect, not something in their own code.

**C5 — Corrupted/duplicated `_MetaInfo.json`** `[Tier A]`
- *Signature:* every compilation fails with a `Newtonsoft.Json` deserialization error deep in
  `Terrasoft.Core.ContentGeneration.ConfigurationMetaInfoReader` / `WorkspaceBuilder.BuildInternalNetStandard`.
- *Verify:* the stack trace itself is the evidence — `_MetaInfo.json` is a file on disk, not a Creatio
  record, so no further on-platform read narrows it.
- *Recommendation:* back up and delete `Terrasoft.WebApp\conf\_MetaInfo.json` (it regenerates), then run a
  full compilation; also check for duplicate `_MetaInfo.json` files. On a cloud environment this needs a
  support/admin request rather than direct file access.

**C6 — "Invalid column name" (DB out of sync with metadata)** `[Tier A]`
- *Signature:* a compiler/SQL error naming a specific column that visibly exists in the object designer.
- *Verify:* call `creatio_describe_object` on the named object's own entity set (see `rca-env-readonly-query`) — if the
  column from the error appears in its properties, that confirms the compiled/designer-visible metadata
  says the column should exist, supporting "the DB structure needs updating" over "the column doesn't
  exist". (`SysSchemaProperty` looked like a fit but live verification showed it's a generic name/value
  property bag, not a column list — don't use it here.)
- *Recommendation:* run "Update database structure" for the affected object, then generate source code and
  recompile. Note that the root cause is usually an earlier failed installation/structure update.

**C7 — 500 after an update: stale `EntitySchemaColumn` UId in QuickAdd config** `[Tier B]`
- *Signature:* `Terrasoft.Common.ItemNotFoundException: 'EntitySchemaColumn' ... with unique identifier
  '{...}' not found`, thrown from `ConfigurationSectionHelper.GetQuickAddConfig`; users see a stuck loading
  screen / 500 after login, right after a platform update.
- *Verify:* needs the **UId from the pasted exception text**. On-platform corroboration is **unconfirmed**
  — live verification of `QuickAddMenuItem` (see `rca-env-readonly-query`) found no field that obviously links
  to an `EntitySchemaColumn` UId. Try a text scan of `QuickAddMenuItem`/`QuickAddMenuSettings` for the UId,
  but don't present it as confirmed corroboration if nothing matches — this case leans closer to Tier B
  in practice than a clean Tier A.
- *Recommendation:* fix or remove the orphaned QuickAdd/setup-data record, then regenerate code and
  compile. If the source of the stale reference is unclear (the common case here), escalate to the update
  team with the UId rather than guessing further.

**C40 — Generated code out of step after a delivery (`CS0103` on a name nobody wrote)** `[Tier A]`
- *Signature:* after a package or application install, the build fails with `error CS0103: The name
  '<name>' does not exist in the current context`, naming an identifier that is in nobody's source —
  typically inside an autogenerated file of the delivered package. The requester's own wording is the
  tell: "it throws `CS0103` on some name that isn't in our code at all."
- *Verify:* in `CompilationHistory`, the failing entry's `FileName` is an autogenerated source of a
  package **this delivery carried** (`installation.md` §5.2 read 2 establishes the ownership).
  The gate must have returned "the delivery broke the build" or "not established" — if it returned "the
  build was already broken", this is not the entry.
- *Recommendation:* run "Generate source code for all schemas", then "Compile all", **on this
  environment**. This is the one entry in the delivery family whose fix is a target-side action, because
  what is out of step is the generated code, not the delivered content. If a full regeneration does not
  clear it, it is not this case — check **C41** (the delivered object lost its parent reference) and
  **C45** (the archive was built from an already-failing source) before repeating the advice.

**C41 — The delivered object lost its parent reference (`CS0103` on `CreateIdColumn` and friends)** `[Tier A]`
- *Signature:* `error CS0103: The name 'CreateIdColumn' does not exist in the current context` — also
  `CreateCreatedByColumn`, `CreateModifiedOnColumn` — in the autogenerated file of an object schema. The
  generated class has no base methods at all, because the schema's parent is missing from its metadata.
  Users describe it as a floating error: "what even is `CreateIdColumn`?"
- *Verify:* read `SysSchema` for the object named in the `FileName` and check its parent (`ParentId`, see
  `rca-env-readonly-query`) — an entity schema with no parent confirms it. In a delivery, also read that
  schema's `CreatedOn` and compare it with the delivery's start: a schema created inside that window
  arrived with this delivery. **Use `CreatedOn`, not `ModifiedOn`** — verified live on a delivered schema
  and on its package, the `ModifiedOn` that travels in the archive is the **source** environment's and can
  pre-date the moment the element landed here, so it says nothing about when the target received it.
- *Recommendation:* the fix is on the **source** environment: open the object there, set its parent object
  (the base entity, or the proper one for that object), save and publish it, regenerate source code and
  re-export the package. On the target, once the corrected package arrives: generate source code and
  Compile all. Regenerating on the target alone cannot restore a parent reference that is absent from the
  metadata — that is exactly what separates this case from **C40**, whose signature it otherwise shares.

## 2. Custom code & package composition

**C8 — Genuinely missing type/namespace (`CS0246`)** `[Tier B]`
- *Signature:* `error CS0246: The type or namespace name '...' could not be found (are you missing a
  using directive or an assembly reference?)` — the most common "real" (non-stale-code) compilation error.
- *Verify:* read `CompilationHistory` for the exact missing type/namespace and the schema/package it's
  referenced from; confirm whether the defining package exists at all via `SysPackage`. Whether the
  required dll is *physically present* in `Files/Bin` is off-platform (file system) — you cannot confirm
  that part from here.
- *Recommendation:* install the package or place the missing dll (`Files/Bin`) that provides the type;
  verify package dependencies (`SysPackageDependency`); then "Compile all". If the reference comes from
  custom/partner code, route it to that package's developer. Try the **C1** stale-code recipe first if
  nothing looks genuinely missing — C1 and C8 share the same `CS0246` code but different causes.

**C9 — Plain mistakes in custom code** `[Tier A]`
- *Signature:* any compiler error pointing into a `Usr*`/partner package schema — the user often doesn't
  realize the fault is in their own or their partner's code.
- *Verify:* `CompilationHistory`'s `ErrorText`/`FileName` names the package and schema — that alone
  identifies the owner.
- *Recommendation:* state plainly which package/schema owns the error and route the fix to that package's
  developer (the customer's dev team or the partner/vendor). The RCA agent never edits code, and never on
  production regardless of who owns the fix.

**C10 — Custom object collides with a base type name** `[Tier A]`
- *Signature:* an ambiguous/duplicate-type compilation error (e.g. a custom `ErrorReason`) right after
  adding a new custom object.
- *Verify:* scan `SysSchema` (see `rca-env-readonly-query`) for the colliding name to confirm both the custom
  and base definitions exist.
- *Recommendation:* rename or remove the custom class/object, regenerate source code, recompile. Recommend
  prefixing custom entities (`Usr*`/company prefix) going forward to avoid recurrence.

**C11 — Unsupported C# language feature (`CS8370`)** `[Tier A]`
- *Signature:* `error CS8370: Feature '...' is not available in C# 7.3. Please use language version 8.0 or
  greater` (or similar) in a partner/custom package.
- *Verify:* the error text itself states the required vs. available language version — no further
  platform read narrows it.
- *Recommendation:* rewrite the offending construct to the environment's supported language version, or
  note that upgrading the environment is the alternative. Do not recommend forcing `LangVersion` in a
  regular package's csproj.

**C12 — Package composition defects (empty/broken csproj; virtual object as Parent)** `[Tier B]`
- *Signature:* MSBuild fails inside a package project itself (not on hand-written code); or errors around
  an entity whose Parent Object is a virtual schema (e.g. `BaseFolder`).
- *Verify:* the "virtual parent" variant has a partial on-platform check — read `SysSchema.ParentId` for
  the named object and see whether the parent's `Name` matches a known platform virtual/base schema (e.g.
  `BaseFolder`). This is a **name-based judgment call, not a confirmed flag** — `SysSchema` has no verified
  `IsVirtual`-style column, so treat a match as corroborating, not proof. The "empty/corrupted csproj"
  variant is a file-system fact this MCP cannot read at all.
- *Recommendation:* virtual parent: change the object's Parent Object from the virtual schema to a proper
  entity, republish, recompile. Empty/corrupted csproj: delete the package's `.csproj` file and let it
  regenerate, then recompile — describe this as a manual step.

**C13 — Schema names differing only by letter case** `[Tier A]`
- *Signature:* static-content generation / compilation fails after two schemas were created whose names
  differ only in case (e.g. `UsrOrder` vs `usrOrder`).
- *Verify:* scan `SysSchema` names case-insensitively (see `rca-env-readonly-query`) for a near-duplicate.
- *Recommendation:* rename one of the schemas so the names differ by more than case, then regenerate
  content and recompile. Recommend avoiding case-only distinctions in schema names entirely.

**C14 — Leftovers of a deleted package** `[Tier A]`
- *Signature:* assorted compilation errors referencing schemas of a package the user says was deleted some
  time ago; or a `Package with name '...' not found in topology` console error right after a deletion.
- *Verify:* confirm the package is gone from `SysPackage`, then check `SysPackageDependency`/
  `SysInstalledApp` for rows still pointing at it (see `rca-env-readonly-query`).
- *Recommendation:* remove the dangling dependent references, run full source generation + "Compile all",
  and regenerate static content. A "not found in topology" console message right after a deletion is
  usually cleared by a restart + full compile. Recommend checking dependencies before deleting a package.

**C15 — `System.Data.SqlClient` unsupported on .NET 6+/Linux** `[Tier B]`
- *Signature:* errors compiling or loading `System.Data.SqlClient` on a .NET 6+ environment or Linux —
  the legacy ADO.NET provider is no longer supported there.
- *Verify:* the error text plus knowing the environment is .NET 6+/Linux is sufficient to recognize the
  case; there is no further platform read that narrows it — the fix is a source/csproj change.
- *Recommendation:* replace `System.Data.SqlClient` with `Microsoft.Data.SqlClient` in the code; for
  assembly packages, add the correct `PackageReference` in the csproj. Recommend reviewing all legacy
  ADO.NET usages when migrating to .NET 6+.

**C16 — OOTB reference assembly not published (`IsPublic = 0`)** `[Tier A]`
- *Signature:* a core/foundation package (e.g. one exposing `IntegrationApi.dll`) fails to compile on
  **every** environment of that build, which the user finds surprising since they never touched it.
- *Verify:* read `SysPackageReferenceAssembly` (see `rca-env-readonly-query`) for the assembly named in the
  error; report its `IsPublic` value. Comparing against a healthy environment of the same build (if the
  user can provide one) strengthens the finding.
- *Recommendation:* if `IsPublic = 0`, the fix is a manual admin/SQL step
  (`UPDATE SysPackageReferenceAssembly SET IsPublic = 1 WHERE Name = '<assembly>.dll'`) followed by a
  recompile — describe this as the recommended action; the RCA agent does not execute it.

**C17 — Anomalous `Terrasoft.Configuration.Dev.csproj` / rogue `ProjectReference`** `[Tier B]`
- *Signature:* `CS0246` on types that clearly exist (e.g. `AngleSharp`, `RemindingUtilities`) inside
  `Autogenerated\Src`; build-order anomalies in the log; often intermittent (fails, then passes on retry).
- *Verify:* the `CompilationHistory` error pattern (types that exist, intermittent failure) is the
  recognizable signature; the actual root artifact — `Terrasoft.Configuration.Dev.csproj` and package
  `.csproj` files — is a file on the server, not readable via this MCP. There is no on-platform
  corroboration beyond recognizing the pattern.
- *Recommendation:* inspect `Terrasoft.WebApp\Terrasoft.Configuration\Terrasoft.Configuration.Dev.csproj`
  and package `.csproj` files (a human/admin step): restore missing OOTB references, remove anomalous
  `ProjectReference` entries pointing at `Terrasoft.Configuration.Dev.csproj`; recycle the app pool,
  restart, "Compile all". Recommend keeping csproj files unmodified by hand on servers going forward.

**C42 — The package references something the delivery did not carry (`CS0246` / `CS0234`)** `[Tier B]`
- *Signature:* during or right after an install, `error CS0246: The type or namespace name '<type>' could
  not be found (are you missing a using directive or an assembly reference?)`, or `error CS0234: The type
  or namespace name '<name>' does not exist in the namespace 'Terrasoft.Configuration'`. The named type
  belongs to a third-party library, a helper schema, or a schema in another package. The requester usually
  does not recognize the name at all — "what `Google`?" — because it comes from the package's own code.
- *Verify:* `CompilationHistory` gives the missing type and the package referencing it. Check `SysPackage`
  for the package that should define it and `SysPackageDependency` for the declared dependency (see
  `rca-env-readonly-query`). Then compare against the delivery's package list (`installation.md` §5.2
  read 2): a defining package that is **neither in the archive nor on the target** means the archive was
  incomplete. Whether a required dll is physically present in `Files/Bin` is a file-system fact this
  platform cannot read — say so rather than implying you checked.
- *Recommendation:* install the package or place the assembly that provides the type **before** the main
  package; correct the package's declared dependencies on the source, re-export and reinstall; then
  "Compile all". If the code is custom or partner-made, the fix belongs to that package's developer.
  **Same error codes as C8, different question:** C8 asks why the type is missing on this environment,
  this entry asks why it did not travel with the archive — answering the delivery case with C8's
  stand-alone reading sends the requester looking for the library on the wrong environment.

**C45 — The archive was exported from an environment that was already failing** `[Tier B]`
- *Signature:* assorted compilation errors on the target that mirror the state the source was in when the
  package was exported; the requester has already fixed the source and reinstalled the same archive with
  no change: "we fixed the errors on dev, but the package still won't install on prod." There is no single
  error text for this case — the shape is *the errors do not correspond to anything on the target, and
  re-installing the same file reproduces them exactly.*
- *Verify:* the failing projects belong to packages this delivery carried (`installation.md` §5.2
  read 2), and the errors survive a full source generation plus "Compile all" on the target — which rules
  out **C40**. The decisive fact, the source environment's build state at export time, lives on another
  environment and cannot be read from here: confirm this side, ask the requester for the other, and say
  which half rests on their account.
- *Recommendation:* rebuild the archive. On the source: fix the errors, run a full source-code generation
  and a clean full compilation, and only then export. **An archive carries the generated state it was
  built from, so an export made before the fix stays broken however many times it is installed** — the
  recommendation is to replace the file, not to retry the install. On the target, nothing needs correcting
  in the delivered package itself.

**C46 — A separate-assembly package arrived with a prebuilt assembly older than its source** `[Tier B]`
- *Signature:* a build that ran inside a delivery fails with `CS0117` (`'<Type>' does not contain a
  definition for '<Member>'`) or `CS1061` in a file of an ordinary package, where `<Type>` belongs to a
  package **compiled into a separate assembly** that the same delivery carried — and the delivered source
  of that type **has** the member. The compilation record's description lists only the ordinary
  package(s) under `Compilation of packages:`; the separate-assembly package is not among them.
- *Verify:* four reads, all `[observed]` on a reproduced delivery:
  1. `SysPackage` for the package that owns `<Type>` — `Type = 1` (compiled into a separate assembly;
     see `rca-env-readonly-query`).
  2. `CompilationHistory` for the delivery's compilation — only `Terrasoft.Configuration.Dev.csproj`, no
     `<Package>.csproj` row: the separate-assembly package was not built during this install.
  3. The delivered source of `<Type>` — the `.cs` attachment on the delivery's `Create` / `Update` child
     for that schema (`rca-cal-file-read`) — contains `<Member>`.
  4. `PackageCompilationState.NeedCompile = true` for that package.

  The mechanism: a separate-assembly package that was built on the source before export travels with its
  compiled assembly. The installer rebuilds such a package only when that assembly is missing or cannot
  be loaded — it does not compare it with the source — and the configuration then compiles against the
  delivered assembly. A member added to the source after the last build there is therefore in the
  delivered code and missing from the delivered assembly. The assembly itself cannot be read from here, so
  report it as the reading the four reads support, not as a fact you opened. Without the attachment
  (read 3), reads 1, 2 and 4 make it the likely reading only — say so.
- *Recommendation:* **Unblock on the target:** "Compile all" — a full compilation rebuilds the
  separate-assembly package from its delivered source, then the configuration; a clean result also
  confirms the diagnosis. **Proper fix, on the source:** build the separate-assembly package after its
  last change and before export, then export again — an archive exported earlier keeps the stale assembly
  however many times it is installed. The calling code in the ordinary package is correct; do not change
  it.

**C47 — The delivery declared a class that another package on the target already declares (`CS0101`)** `[Tier A]`
- *Signature:* a build that ran inside a delivery fails with `CS0101` (`The namespace '<Namespace>' already
  contains a definition for '<Type>'`). Neither file is broken on its own: every ordinary package compiles
  into one configuration assembly, so two packages that each declare `<Namespace>.<Type>` collide there,
  although each builds cleanly where it was written. The file the error names — `<Schema>.<Package>.cs` in
  `CompilationHistory.FileName` — holds only **one** of the two declarations, the delivered one or the
  local one; the compilation record's description lists only the delivered package(s) under
  `Compilation of packages:`.
- *Verify:* three reads, all `[observed]` on a reproduced delivery:
  1. The delivered declaration: the `.cs` attachment on the delivery's `Create` / `Update` child for its
     schema (`rca-cal-file-read`) declares `<Type>`.
  2. **The other declaration — find it by content, not by name.** A class need not be named after its
     schema, so a `SysSchema` search by `Name` finds the other one only when the names happen to overlap:
     one such call is a shortcut, and an empty result proves nothing. The reliable read: list `SysFile`
     rows with `RecordSchemaName = ConfActivityLog` and a `.cs` name, created before the delivery, newest
     first, and read each with `get_text_file_content` filtered to the declaration
     (`filterLinesWithRegex`: `(class|struct|interface|enum|record)\s+<Type>\b`). The hit's
     `ConfActivityLog` row names the schema, its package and when it was saved; a row with no `Parent` is
     a save made on this environment, outside any delivery.
  3. That save time against the last clean compilation before the delivery (`installation.md` §5.2):
     saved before it → the environment built cleanly **with** that declaration, and the delivery brought
     the collision.

  No customer `.cs` declares `<Type>` → the other declaration is a platform type: that is **C10**, not this
  entry. Without attachments on the environment's own rows (the switch in `rca-cal-file-read`), read 2
  cannot be made: name the candidates a `SysSchema` search returned and say that the other declaration
  was not read.
- *Recommendation:* **Unblock on the target:** rename the class in the package the delivery did **not**
  bring — the target owns it, while a delivered schema edited on the target is replaced by the next
  delivery of its package — update that class's callers, then "Compile all". If the local class
  duplicates what the delivery now provides, deleting it and pointing its callers at the delivered class
  is the alternative. **Do not offer removing the delivered schema or rolling the delivery back as the
  unblock:** it discards a delivered element that is not broken. **Proper fix:** decide which package owns
  the name, and give each class a name unique across packages — naming the class after its schema is a
  simple rule — or a package-specific namespace. Renaming the local class needs no new export; renaming
  the delivered one is a change on the source, then export and install again. Do not describe either
  file's code as broken.

## 3. UI, timeouts & post-compile behavior

**C29 — Compile "fails" with 504/spinner but actually succeeded** `[Tier A]` — one of the most frequent
compilation cases.
- *Signature:* the UI shows an HTTP transport error (`504 Gateway Timeout` or `0 Unknown Error`) on
  `WorkspaceExplorerService.svc/BuildConfiguration`/`Rebuild`, or an endless spinner — reliably, after a
  few minutes, every time.
- *Verify:* **this is a currency check, not a code-error diagnosis.** Read the latest `ConfActivityLog`/
  `CompilationHistory` for that compilation run — if it shows `Success`/`Warning` (or a later successful
  run exists), the build actually completed and the UI simply gave up waiting for the response (a common
  cause is a proxy/session/request timeout in front of the app, e.g. HAProxy).
- *Recommendation:* don't restart the compilation — wait, then check the real result via Compilation
  history / `VwCompilationErrors`. If it succeeded, the transport error can be ignored; repeated parallel
  restarts are actively harmful (they pile up server load). This is the textbook "current vs. historical /
  don't trust the loudest symptom" case — lead with it.

**C30 — "Terrasoft is not initialized" after compile** `[Tier C]`
- *Signature:* `Uncaught Error: The global object 'Terrasoft' is not initialized` in the browser console
  right after a compilation; the site shows a blank page.
- *Off-platform:* browser console state and CDN/browser cache are not visible via this MCP; `conf\content`
  integrity on disk likewise.
- *Recommendation:* regenerate static content (a full compilation), restart the app pool, and clear the
  browser cache/CDN. If it persists, recommend checking `conf\content` integrity and file locks during
  generation as a server-side follow-up. **Escalate to infra** if regeneration alone doesn't resolve it.

**C31 — "Default workspace assembly not initialized" (500)** `[Tier C]`
- *Signature:* `AssemblyNotInitializedException: The "Default" workspace assembly is not initialized`;
  `LoadWorkspaceAssemblyError: Could not load file or assembly 'CrtCoreBase...'`; a missing
  `CrtWebhookServiceBase.dll`(`.pdb`); or a log line `Application End: A Change Was Made to ... Web.config`
  right around the failure.
- *Off-platform:* which dll is actually missing from `conf\bin\NN` on disk is not visible via this MCP;
  the `Application End`/web.config-restart correlation, if pasted, is a strong recognizable tell.
- *Recommendation:* run a full compilation to rebuild the workspace assemblies. If a specific dll is
  missing from `conf\bin\NN`, restore it (from backup or by recompiling) and restart — a manual server
  step. Recommend avoiding `web.config` edits during/right after a compile (it restarts the app domain
  mid-write). After a .NET migration, also recommend clearing Redis and restarting with cache clearing. If
  dlls vanish repeatedly, recommend investigating antivirus/file-watcher interference. **Escalate to
  infra** for the file restore.
- *Delivery variant — "it installed fine and minutes later the site stopped opening".* The delivery
  reported success, the post-install build failed, and the workspace assembly never initialized — so the
  site serves this exception instead of loading. The build errors behind it are readable: the delivery's
  `Compilation` child and its `CompilationHistory` (commonly `CS0246`/`CS0115` raised from a custom
  package), plus `VwCompilationErrors` for the current state. Run `installation.md` §5.2's gate
  first — a site that goes down after a delivery is the case most often blamed on the wrong side. If the
  build errors are fixable, fix them and run a full compilation; if they are not, restoring from the
  pre-installation backup is the alternative, and that decision goes through the spine's **restore gate**
  (§6) rather than being improvised under outage pressure. Either way the package goes back to its
  developer.

**C32 — Install blocked by "compilation errors on site" despite a clean compile** `[Tier A]`
- *Signature:* a package installation refuses to start, citing compilation errors present on the site, but
  running "Compile all" by hand finishes clean.
- *Verify:* read `VwCompilationErrors` (see `rca-env-readonly-query`) — if it is non-empty while the most
  recent `ConfActivityLog`/`CompilationHistory` compile is clean, the stored error state is **stale**, left
  over from an earlier failed run.
- *Recommendation:* run a **full** "Compile all" (not a partial one) to refresh the stored error state,
  confirm `VwCompilationErrors` is now empty, then retry the installation.

**C33 — Docker container exits after compile** `[Tier C]`
- *Signature:* on a Docker/.NET Core dev stand, the container exits right after a compilation completes;
  the site stays down until someone manually starts it again.
- *Off-platform:* the container's restart policy is a Docker/host-level setting, not visible via this MCP.
- *Recommendation:* this is expected — the app restarts after compilation, which stops a container not
  configured to restart automatically. Recreate the container with `--restart=always`
  (`docker run --restart=always ...`) so it comes back on its own after each compile. No escalation
  needed beyond the dev team owning the compose/run config.

## 4. Permissions & file system

**C25 — No permissions on Temp/Configuration directories** `[Tier C]`
- *Signature:* `UnauthorizedAccessException` / access denied on `tempDirectoryPath` (from
  `ConnectionStrings.config`) or `Terrasoft.Configuration` during compile.
- *Off-platform:* file-system ACLs are not visible via this MCP.
- *Recommendation:* grant the IIS app-pool user full rights on `tempDirectoryPath`, `Terrasoft.Configuration`,
  and the site directories; restart the pool; recompile. **Escalate to infra/support** for the permission
  grant.
- *Delivery variant — `CS2001` on a temporary compilation directory.* During a delivery the same
  directory problem surfaces as `error CS2001: Source file '…\Temporary ASP.NET Files\…' could not be
  found`. **The real cause sits higher in the installation log** — a line reporting that the directory
  could not be deleted — so the `CS2001` entries are consequences and there is nothing wrong with the
  delivered package. Read the log around the failure (`installation.md` §2.2) before attributing
  anything to the archive. Fix: stop the application pool, clear the site's temporary compilation
  directory, confirm the pool user's rights on it, start the pool and recompile.

**C26 — Locked `ODataEntities.dll` / "OData entities compilation errors"** `[Tier B]`
- *Signature:* `Compilation error: access to Terrasoft.Configuration.ODataEntities.dll is denied`, or the
  message "OData entities compilation errors occurred. Please recompile the app via Configuration section."
- *Verify:* the message text distinguishes the two sub-cases; which process/service is holding the file
  lock is a server-level fact (running processes) not visible via this MCP.
- *Recommendation:* locked dll: restart the site/app pool to release the file (identifying and stopping the
  specific culprit process — a custom service, antivirus — is a manual server-side step); "OData entities
  compilation errors" message: run "Generate source code for all schemas", then "Compile all".

**C27 — Path length over 260 characters** `[Tier C]`
- *Signature:* `DirectoryNotFoundException` or a path-related crash during compile/content generation,
  with a very long path visible in the error (near 260 characters) — typically a long site root + long
  schema/package names.
- *Off-platform:* the actual full path length on disk is not visible via this MCP, though long
  schema/package names contributing to it (`SysSchema.Name`, `SysPackage.Name`) can be read as a partial
  corroborating signal.
- *Recommendation:* shorten the source of the length — schema/SQL-script names, the package name (via
  clio), or move the site to a shorter root path; clear `Files\obj` and recompile. Note that on
  Windows/.NET Framework the 260-character limit is hard — recommend planning names accordingly.
  **Escalate to infra** for the site-path move.
- *Delivery variant — during an install or an export, on a resource file.*
  `System.IO.DirectoryNotFoundException: Could not find a part of the path '…resource.<culture>.xml'`,
  where the path visibly contains one very long element name. Find that element in the failing path — a
  schema or a SQL script — and shorten it **on the source**, check the package for other long names, then
  re-export and reinstall. Reinstalling the same archive without shortening the name reproduces it
  exactly, which is what makes this look like an environment problem when it is a naming one.

**C28 — Space (`%20`) in the site folder name** `[Tier C]`
- *Signature:* the app won't start after deployment; logs show `access to NuGet\Migrations is denied` or
  `e_sqlite3.dll not found` at a path containing `%20` (a URL-encoded space).
- *Off-platform:* the hosting directory name is not visible via this MCP — `%20` in the pasted log/path is
  the recognizable tell.
- *Recommendation:* remove spaces (and special characters) from the site's directory name; redeploy/repoint
  IIS; grant permissions to the NuGet cache directories for the pool user; recompile. **Escalate to
  infra/deployment** — this is a hosting-path decision, not a configuration fix.
- *Delivery variant — the space is in the package's Maintainer, not in the site path.* `[Tier A]` A
  package whose Maintainer (publisher) name contains a space or a special character produces compilation
  errors in that package's autogenerated files once it is delivered. This half **is** readable here:
  `SysPackage.Maintainer` holds the value for the delivered package (verified live as a readable column),
  so name what it actually contains instead of inferring it. Fix on the source: remove spaces and special
  characters from the Maintainer — and from the publisher setting used when packages are created — then
  re-export the package and recompile on the target.

**C44 — `Value for argument "hash" must be specified` — the package name makes the build path too long** `[Tier C]`
- *Signature:* `Terrasoft.Common.ArgumentNullOrEmptyException: Value for argument "hash" must be
  specified`, usually accompanied by `File does not exist at the following path:` pointing at a generated
  MSBuild editor-config file under the package's `Files\obj\Release`. The underlying cause is the full
  build path exceeding the operating system's limit because the package name is very long; a missing local
  build component produces the same shape, which is why the message alone does not identify the cause.
- *Off-platform:* the build path on disk and the presence of the build components are file-system facts
  this platform cannot read. `SysPackage.Name` **is** readable, and a conspicuously long package name is
  corroborating — say it is corroborating, not proof.
- *Recommendation:* manual steps for whoever owns the environment: clear the contents of the problem
  package's `Files\obj\Release` (an export will not work otherwise), export the package, shorten the
  package name (clio can rename it), import it back and recompile. Also confirm no package name exceeds
  the length of the base packages' names, and that the required build components are installed. Same
  family as **C27** — path length — but a different signature and a different fix.

## 5. Server environment (.NET / SDK / infra)

**C18 — Wrong/missing .NET SDK** `[Tier C]`
- *Signature:* `It was not possible to find any installed .NET Core SDKs`; or `NuGet.targets: error :
  Error loading lock file '...project.assets.json' : '<' is an invalid start of a property name`; or
  `NU1101` on basic packages; a non-informative UI error ("See logs for more details") right after a fresh
  on-site deployment.
- *Off-platform:* the installed SDK version, `global.json`, and the `DOTNET_CLI_HOME` environment variable
  are all server-side facts — no platform read confirms them.
- *Recommendation:* install exactly the .NET SDK version required by the Creatio version (system
  requirements page); remove/limit unsupported newer SDKs, or pin the version with a `global.json` in the
  app root; check `DOTNET_CLI_HOME` is set for the app-pool user; clear `Files\obj` and recompile.
  **Escalate to infra/support** with the compilation log if the environment isn't directly accessible.

**C19 — Cloud dotnet/MSBuild failure, server-wide** `[Tier C]`
- *Signature:* "An error occured while running dotnet restore/build" on a cloud environment; the same
  MSBuild errors appearing on **multiple/all sites** hosted on one server/block, starting at the same time.
- *Off-platform:* this is an infrastructure-level fact (which sites share a server/block) that this MCP
  has no way to confirm — you only see the one connected environment.
- *Recommendation:* do not attempt config-side fixes for what looks like a server-wide pattern.
  **Escalate to cloud/infra**, referencing the server/block if known; after their fix, each affected site
  needs one full compilation to clear stale errors.

**C20 — NuGet restore fails in a closed network (`NU1101`)** `[Tier C]`
- *Signature:* `NU1101: Unable to find package Microsoft.NetCore.Platforms. No packages exist with this id
  in source(s): root packages` — typically on an on-site environment with no internet access.
- *Off-platform:* network/proxy configuration and the NuGet feed setup are server-side, not visible via
  this MCP.
- *Recommendation:* Creatio's compilation uses standard SDK-style projects resolving from the default
  `nuget.org` feed (no proprietary Creatio feed). Options: allow `nuget.org` through a proxy, or set up an
  internal NuGet mirror with the required basic .NET packages and configure it as the source. **Escalate
  to infra** if the client needs the exact package list — it can be read from a test compile's restore log
  on that environment.

**C21 — Microsoft Build Tools broken at server level** `[Tier C]`
- *Signature:* `Could not load file or assembly 'Microsoft.Build.Framework, Version=15.1.0.0, Culture=neutral,
  PublicKeyToken=b03f5f7f11d50a3a'`; compilation fails via one interface (e.g. WorkspaceConsole) but may
  work via another (e.g. the UI).
- *Off-platform:* Build Tools installation state and MSBuild resolution on the server are not visible via
  this MCP.
- *Recommendation:* repair/reinstall Microsoft Build Tools; check for extraneous .NET components hijacking
  MSBuild resolution; verify the executing user's access rights; compare with a healthy server. If one
  interface still works, note it as a temporary workaround. **Escalate to infra** — this is a server
  environment problem, not a Creatio configuration issue.

**C22 — SQLite malformed / readonly** `[Tier C]`
- *Signature:* `Microsoft.Data.Sqlite.SqliteException: SQLite Error 11: 'database disk image is malformed'`
  (site fully down, HealthCheck shows it); or "attempt to write a readonly database" / per-node permission
  errors on a web farm.
- *Off-platform:* the SQLite file's integrity and file-system permissions on every web-farm node are not
  visible via this MCP.
- *Recommendation:* malformed image: rebuild it via the platform's `BuildConfiguration` scripts (on cloud,
  via a support request with the provided bat files, sending the logs). Readonly/permissions: grant the
  app-pool user write rights to the site root/SQLite file on **every** web-farm node. After the fix, run a
  full compilation. **Escalate to infra/support** for the rebuild step on cloud.

**C23 — Outdated ICU on Linux (post-upgrade)** `[Tier C]`
- *Signature:* `'Index was outside the bounds of the array'` inside `CreateCulturesScript`; logs point at
  `libicu*.so.50`; seen after upgrading an older Linux distribution (e.g. Amazon Linux 2) to a newer
  Creatio/.NET major version (e.g. 8.3.0/.NET 8).
- *Off-platform:* the installed ICU library version on the OS is not visible via this MCP.
- *Recommendation:* .NET 8 no longer falls back on incomplete ICU data — update the ICU libraries on the
  server to a version .NET 8 supports, then restart the app. **Escalate to infra**; recommend checking
  OS-level prerequisites whenever a Creatio major-version upgrade is planned on an older Linux distribution.

**C24 — `nlog.config` copied from another environment** `[Tier C]`
- *Signature:* `Exception occurred in Nlog` right at the start of compilation, typically after deploying a
  **copy of another environment** (e.g. prod → on-site) on-site.
- *Off-platform:* the contents of `nlog.config` on disk are not visible via this MCP.
- *Recommendation:* use a clean `nlog.config` for the copy (the default from the distributive of the same
  version) instead of reusing the source environment's logging targets/paths; restart and recompile. This
  is a file-system fix — describe it as a manual step; **escalate to the deploying admin** if you can't
  confirm which file was copied.

**C43 — Deadlock while saving schema resources during an install** `[Tier B]`
- *Signature:* the delivery fails with `Error occured while saving resources for schema '<schema>' in
  '<package>' package for '<culture>' culture`, whose inner exception is a database deadlock —
  `Transaction (Process ID …) was deadlocked on lock resources … and has been chosen as the deadlock
  victim`. Repeating the install reproduces it rather than clearing it.
- *Verify:* the paired message plus the deadlock is the signature, and it comes from the installation log
  (`installation.md` §2.2), not from `CompilationHistory` — this failure happens while the
  delivery writes resources, so there may be no compiler diagnostic at all. The asynchronous
  resource-saving optimization behind it is controlled in the **application's configuration file**, not by
  a system setting or a feature, so it cannot be read from here: do not report a value for it, and do not
  go looking for it among settings.
- *Recommendation:* disable the asynchronous saving of schema resources during installation in the
  application configuration, then retry the delivery — a manual step for whoever owns the environment, and
  on cloud a support request rather than a customer-side change. Because deadlocks are contention-driven,
  retrying the install in a quiet window is a legitimate temporary unblock while that change is arranged;
  say plainly that it is a workaround, not the fix.

## Boundaries (this file's coverage)

**Covered:** the error-signature cases, by category — stale/generated metadata (C1–C7,
**C40–C41**), custom code & packaging (C8–C17, **C42**, **C45**–**C47**), UI/timeouts & post-compile (C29–C33),
permissions & file system (C25–C28, **C44**), server environment (C18–C24, **C43**). All supporting
entities behind these cases (`VwCompilationErrors`, `SysPackageReferenceAssembly`,
`PackageCompilationState`, `SysPackage`/`SysPackageDependency`/`SysInstalledApp`, `SysSchema`) were
**verified live via `creatio_describe_object`** (see `rca-env-readonly-query`) — not assumed. That pass
corrected two original assumptions: `SysSchemaProperty` does not list an object's DB columns (C6 uses
`creatio_describe_object` on the object itself instead), and `QuickAddMenuItem` does not expose an obvious
link to the missing UId in C7 (treated as closer to Tier B in practice).

**Tier B/C entries are intentionally partial** — they recognize the signature and give the known fix, but
say plainly when evidence (server, file system, browser) cannot be verified from this platform and route
to infra/support instead of presenting a guess as a confirmed diagnosis. This is by design (the legend
above), not a gap.

**The delivery family.** Eight of the cases above (C40–C47) and four *Delivery variants* (on C25, C27, C28,
C31) cover a build that ran as a stage of a package or application installation. They are matched the same
way as everything else here — by signature, after the partition — but only **after**
`installation.md` §5.2 has returned its verdict on whether the delivery caused the failure at all.
Their fixes mostly act on the **source** environment and the archive. Only C40's fix acts on the target;
C46's *unblock* does too — a full compilation rebuilds the stale assembly — while its fix stays on the
source; and C47's unblock acts on the target's own package, the one the delivery did not bring.
Recommending C40's "regenerate and compile all" for any of the others is the characteristic error this
family exists to prevent.

**Not here:** warnings (C34), advisory/consultation topics (C35–C38), and the cross-turn currency rule
(C39) — see `compilation-catalog-reference.md`. Also not covered: web-farm compile
specifics, .NET Framework vs. Core differences, clio compile commands, CI/CD automation, a Build.log
reading guide.
