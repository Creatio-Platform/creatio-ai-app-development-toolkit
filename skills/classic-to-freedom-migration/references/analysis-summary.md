# App Structure Analysis Summary (user-facing response)

After analyzing the Classic structure (Workflow steps 0–5), present the plan in chat in two parts:

1. **This summary** — `Overview`, `What it does`, `Pages` — orients the reader on scope, size and which
   screens move where. Short and scannable.
2. **The per-page design spec** — generated by `node engine/migrate.mjs <manifest> --spec` and presented
   **verbatim** (see `references/page-design-spec.md`): one `Layout` table (structure + contents), a
   `Logic` table (behaviour), and the `⚠ Confirm before I build` worklist. This is the "what goes where".

The dense provenance lives in `plan.md`.

## Format Rules

- **Plain Markdown in chat. Never HTML, never an artifact, never a rendered page.** Headings, short
  lists, narrow tables only.
- Match the user's language.
- **Overview meta on three lines with bold labels.** Put `**Scope:**` / `**Environment:**` / `**Package:**`
  on THREE separate lines (one per item). End each of the first two with ` ·` and a hard line break (two
  trailing spaces) so they render stacked.
- **Every fact lives in ONE place — never restate it.** scope → the `Scope` line; owning/target package +
  lock state → the `Package` line; per-item migration call → the `Pages` table; each field's/detail's
  placement, type, rule → the design-spec `Layout` table; behaviour (filters/handlers/process) → `Logic`;
  decisions + risks → `⚠ Confirm`. If a line repeats something already shown above, cut it.
- Scale to scope. **Single-section:** `Overview` + `What it does` + `Pages`, then the design spec. No
  phases. **Whole-package:** add `How we'll stage it`, and give `Pages` a leading `Section` column that
  repeats down its rows.

Migration call vocabulary (the `Call` column in `Pages`):

| Call | Meaning |
| --- | --- |
| **Rebuild** | Own section/page → a new parallel Freedom list/form page. |
| **Delta** | Replacing/extension schema → additive change on an existing Freedom page. |
| **Reuse** | Server-side (entity/details/lookups/process/code) — no UI work; left in place. |
| **Manual** | No safe Freedom analog — needs a product/architecture decision first. |
| **Drop** | Intentionally not migrated (record the reason). |

## Structure

```
## <App / section name> — Classic → Freedom UI

### Overview
**Scope:** <single-section | whole-package> ·
**Environment:** <name or "repository only"> ·
**Package:** <owning package (lock state) → target package>

- **Size:** <P> pages · <F> fields · <R> page rules · <D> details/features
- **Approach:** <strategy in ONE sentence — parallel rebuild / reconcile / switch-over. Do NOT restate the
  package, lock state or scope — those are the lines above.>

### What it does
<1–2 sentences in business language: what the app is for and who uses it.>

### Pages
| Classic | Freedom target | Call |
| --- | --- | --- |
| <section/list schema> | <Freedom list template> | Rebuild |
| <page schema> | <Freedom form template> | Rebuild |
| entity · details · lookups · backend | reused as-is | Reuse |
```

Then present the per-page design spec (`--spec` output) for each Rebuild/Delta page, and stop for
explicit approval. Do not stop on the summary alone — the user approves the design spec.

Whole-package only, before the design specs:

```
### How we'll stage it
- **Phase 1 — <name>**: <sections/pages>, why first (highest traffic, fewest dependencies).
- **Phase 2 — <name>**: <sections>, gated by <prerequisite/decision>.
- Order: entities/data sources → own sections → replacing/extension deltas → backend.
```

## Worked Example (single-section, abbreviated)

```
## Applicants — Classic → Freedom UI

### Overview
**Scope:** single section (record page + list) ·
**Environment:** workbuild103_15688915_0726 (runtime confirmed) ·
**Package:** HRApplicant / HRRequest / WorkHrBase (Classic, locked) → new UsrApplicantFreedom

- **Size:** 2 pages · 19 fields · 6 page rules · 8 details/features
- **Approach:** parallel rebuild over the existing Applicant entity — Classic stays live, no switch-over.

### What it does
The HR/Recruiting candidates register — each applicant card carries a contact/vacancy profile,
recruitment-stage logic, communications, activities/emails, and an approvals (visa) flow.

### Pages
| Classic | Freedom target | Call |
| --- | --- | --- |
| Applicant1Section | ListPageV3 list page | Rebuild |
| Applicant1Page | PageWithTabsFreedomTemplate (form) | Rebuild |
| Applicant entity · details · lookups · backend | reused as-is | Reuse |
```

Then the generated design spec (`Layout` + `Logic` + `⚠ Confirm`) for `Applicant1Page` follows.
