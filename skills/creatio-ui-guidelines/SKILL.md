# Creatio UI guidelines

Use this skill to help agents create or review Creatio Freedom UI pages that look native, are understandable for end users, and meet accessibility expectations.

**Design as a UI/UX expert, not as a data-model dump.** Before composing or editing a page, mentally walk through how a real user will actually fill it in and use it: the order they enter data, what they need to understand at each step, what would confuse or slow them down, what they look at most often. Make deliberate design decisions and justify them with established UX heuristics and best practices — clarity, recognition over recall, error prevention, consistency, progressive disclosure, and minimal effort. A page is not "done" when the fields exist; it is done when it is genuinely easy and pleasant to complete and use.

**Judge the rendered page, not the schema.** When reviewing or auditing an existing page, base your findings on the actual RENDERED page (screenshot + live accessibility tree), and walk the fill scenario first — only then reconcile with the schema/metadata. Many defects are visual-only and invisible in the schema or a11y tree: empty/unbalanced islands, group headers that don't render, weak placeholders, spacing/proportion issues. "Looks fine in the schema" is not evidence the page is fine.

**Rules are the floor, not the finish.** A page can satisfy every rule here and still look wrong — a leftover border on an island, a corner radius the native page does not have, a block that answers no question. Two habits close that gap: decide what the page is for before placing anything (`./references/design-judgement.md`), and compare the rendered page with a native Creatio page on the same template before calling it done (`./references/visual-check.md`). When a general-purpose design skill (frontend-design, ui-ux-pro-max, taste and the like) is loaded too, this skill wins for Freedom UI pages: the native look over a distinctive one.

## Product telemetry — this skill has no workflow of its own

This is an **overlay**: it supplies naming/design rules to whichever flow is running, and it never owns a
run. Do **not** emit a separate telemetry session for it — the enclosing flow (app creation, migration,
mobile conversion, branding) already reports its own stages, and a second session would double-count.

The one exception is running **standalone**: if the developer invoked this skill directly and no other
CAADT flow is active, yet the run goes on to change the environment, that run is a targeted edit — emit
the `app-maintenance` stages from `../../context/product-telemetry.md` (`workflow_started`,
`plan_skipped`, `work_item_completed`, `workflow_completed` / `workflow_failed`) so the change is not
invisible. Telemetry is non-blocking and never gates the review or the edit.

## Operating mode

1. Clarify the page goal only when the task cannot proceed without it. Prefer best-effort recommendations over blocking.
2. Identify user roles, main scenarios, data-entry frequency, and whether the page is for create, view, edit, approval, or analytics.
3. Reuse Creatio/Freedom UI patterns before inventing custom controls. Search for analogous Creatio functionality in the target app and align layout, labels, actions, states, and behavior.
4. Produce outputs in one of these forms depending on the user request:
   - page structure proposal;
   - implementation instructions for a Creatio builder/developer agent;
   - UI/UX audit with issues, severity, and fix recommendations;
   - accessibility/WCAG review;
   - copy/label/error text rewrite;
   - acceptance criteria/checklist.
5. Always include an explicit review checklist before finalizing a design or audit.

## References — read the matching one BEFORE you act (required, not optional)

The rules above are only a reminder. The detailed specifics that agents get wrong — exact component names, the concept→component map, grid/column math, gap rules, contrast values, audit templates — live in the references. Do NOT rely on this summary or on memory. For the task at hand, open the matching reference and follow it before producing a design, an edit, or an audit:

- **Creating, editing, laying out, or reviewing a page** — placing/ordering fields, groups, tabs, profile islands, details/child lists, lookups, buttons, layout/`layoutConfig` → **before you act, look up `./references/page-layout-and-controls.md` by section: list its headings (`grep -n '^#'`), then read the section for the element you are placing** (start with its "Choosing the component (source of truth)" — resolve component names via `get-component-info`, never from memory).
- **Anything about accessibility, contrast, color, charts, tabs, or custom components** → **before you act, look up `./references/accessibility-and-colors.md` by section: list its headings, then read the section for the element you are placing**.
- **Producing an audit, review, or acceptance checklist** → **read `./references/review-checklists.md` whole only for a full audit** and use its severity model and output templates; for one check, look up its section by heading.
- **Deciding what goes on the page** — the page's question, page kind and template, where information goes, which container, how dense, which chart, confirm or undo → look up `./references/design-judgement.md` by section; for a known kind of page (list, record, worklist, dashboard, step-by-step, approval, settings) read its pattern in `./references/page-patterns.md`.
- **Judging how the page looks** — hierarchy, grouping, the colour budget, states, the tells of generated pages, what native Creatio looks like → look up `./references/visual-judgement.md` by section.
- **Writing captions, messages, errors, confirmations, empty states** → look up `./references/ux-writing.md` by section.
- **Checking the rendered page** — computed styles against a native page on the same template, zoomed crops, overflow, a blind critic → look up `./references/visual-check.md` by section.

When a task spans several of these, look up the matching section in each relevant reference. Skipping the matching reference is the main cause of the recurring defects (selection-window lookups, layout gaps, bare fields, non-native details). **Reading the matching reference is itself part of finishing the work, not a courtesy step** — a page built or reviewed without it is incomplete even if it happens to look right, exactly like any other gated deliverable this skill's caller checks for.

**Read a reference by section, never whole.** List its headings with their line numbers, then read that one section's lines (the file-reading tool's offset and limit, or `sed -n '<from>,<to>p'`). A read with no offset or limit, a full-file shell `cat`, and a series of ranged passes that walks the whole file each cost a full read of `page-layout-and-controls.md`, and a truncated `cat` also hides the part it cut off.

## Default page design principles

Treat the following as non-negotiable unless the user explicitly overrides them:

- **Keep project customizations visually consistent with the base Creatio product — custom additions must not visually stand out.** Use the default component appearance, typography, colors, spacing, and borders of standard Creatio. A customization that makes the page look different from the base product (even if it seems "nicer" in isolation) is a defect, not an improvement. Deviate only when a real business priority requires it — and then as a deliberate, scoped decision, never as a side effect of another change.
- Prefer no-code/Freedom UI components, predefined typography, predefined colors, templates, business rules, dynamic cases, mini pages, DCM (Dynamic Case Management) stage progress bars, widgets, and existing navigation patterns.
- Make the page understandable without separate instructions where possible. Use structure, labels, placeholders, tooltips, FAQ/help, and validation to guide the user.
- Avoid long, unstructured record pages. Group data into logical tabs, field groups, profile islands, metrics/widgets, related record profiles, progress bar and toggle panels.
- **Put required fields on the first screen.** Place them where the user sees them on opening the page — the header or top island, the left profile column, or the first tab — in logical order and with the required mark. Do not hide a required field on a second or later tab, where the user meets it only when saving fails. This is a strong default, not a hard rule: when a required field has to live elsewhere, name the reason in the plan. Frequently edited fields go early too.
- Keep required fields to the real minimum needed to create the record. Mark a field required ONLY if the record is meaningless or cannot be created without it; everything else stays optional (guide it with hints/defaults instead). Over-requiring fields blocks quick creation and frustrates users.
- Use color as a supporting cue, never as the only information channel.
- Validate contrast and accessibility for every custom color, background, chart, tab, image, dialog, and custom component.

## Mandatory implementation rules (most-missed — DO NOT SKIP)

These are the rules agents most often miss. Treat each as a hard requirement and verify it explicitly before finishing any page work.

- **A pre-built combination is a COMPOSITE, not a single type — never hand-build one from raw component types.** "Expanded list", "Attachments", "Next steps", "Communication options", "Approval list", and similar Designer-listed combinations assemble SEVERAL components together (e.g. Approvals = a module/widget above the profile island PLUS the approval list — two components, not one). Get the assembly recipe with `get-component-info composite='<caption>'` and build EVERY part it names — never insert only the part you recognize and treat the rest as optional. This rule was measured to reach the model and still get applied to only some of a plan's composites (not all) — if a spec enumerates a composite's parts, every part is its own required deliverable, not a single row that closes on partial work.
  - **Record which recipe you fetched for every `compositeOnly` type you insert.** When `get-component-info` reports a type as `compositeOnly`, name — in your worklog/evidence, not only in your own reasoning — the exact `composite='<caption>'` recipe you fetched for it and every part that recipe named. A `compositeOnly` type with no recipe named in your evidence is not a machine-blocked stop today (there is no automated gate for this outside the Approvals module/list pair, which IS machine-checked — see the migration engine's `Quality gates` row), but it is a checkable claim: a person or a later run can compare what you recorded against the recipe and catch a partial build the same way this rule's own measurement did.
- **Contrast and accessible-name basics are checked on every page, not only during a dedicated audit.** Standard/small text ≥ 4.5:1 contrast, large text ≥ 3:1 (custom tabs/areas/charts/backgrounds included); every component's accessible name (`Title`/`aria-label`/tooltip/alt) is filled with a real, meaningful value, never left empty or at a placeholder default. These are pass/fail checks, not a "nice to have" reserved for `./references/accessibility-and-colors.md` — apply them while building, then use that reference for anything beyond this baseline (charts, custom components, the full WCAG criteria list).
- **A dense or overloaded layout is a required fix, or a decision to raise — never "refine if desired."** Reread the rendered page against *Default page design principles* above (balance, spacing, grouping) before calling a page done; a layout that only "technically" places every field is not finished work.
- **Few-value lookups MUST be dropdowns, not selection windows.** Any lookup to a small/finite catalog (status, type, category, stage, priority, and similar enum-like sets) must render as an inline dropdown. In Creatio this is controlled at the entity-column level, not by the page: set `simple-lookup: true` on the column (clio `modify`/`add` column op). Standard (non-simple) lookups open the modal selection window — keep that ONLY for large or relationship lookups (Contact, Account, parent record). Never leave a 3–20-value lookup as a selection window.
- **A status-like lookup gets colored chips — on the record page and in every list.** When a few-value lookup's values carry a state or a level the user scans for — status, stage, priority, health, risk, result — make its values colored, without waiting to be asked. Freedom UI then shows the value as a colored chip in the form field and in every list that shows it, with no page change. This skill owns WHICH lookups and WHICH colors: the color follows the value's meaning, the same across the app — good or done green, attention or waiting amber, problem (failed, overdue, red health) red, draft or closed a neutral color — never the order of a palette, and the chip keeps its text, so color is never the only channel; check the chip text's contrast on the rendered page. Do not color a lookup whose values carry no state (country, product line). HOW to set the color column and write the values is owned by clio: read `get-guidance name=lookup-colors` and follow it, taking the colors from this rule. Details: *Fields* in `./references/page-layout-and-controls.md`.
- **Add tooltips and placeholders to help users fill the form — do not ship bare fields.** Guidance is required where it adds value, not blanket on every field. A field that is not self-explanatory needs a `placeholder` showing the sample value or format, and/or a `tooltip` for longer explanations — what the field means, its units/scale, allowed values, or (for read-only/calculated fields) how and when it is filled. Always add a `tooltip` to read-only/calculated fields explaining their source.
  - **Scope — placeholders are NOT mandatory on every field.** Add a `placeholder` to free-entry inputs where an explanation or format genuinely helps (text/number/date/email/phone/web — e.g. a code, phone, amount, or date format). Skip it for self-evident fields and for controls that don't use a free-text hint — lookups/ComboBox (the dropdown already shows the options) and checkboxes (the label says it). Do not pad obvious fields with filler just to "have" a placeholder — an unnecessary placeholder is as bad as a missing helpful one.
  - **Write text that genuinely helps — specific to the field, not generic filler.** "Enter value" or repeating the label is useless. Use a placeholder OR a tooltip OR both, whichever the field needs: a placeholder when an example/format makes the field self-evident (a formatted field → show the format, e.g. a supplier code as `SUP-00123`; a date field with the date picker usually needs none, and any date hint must follow the user's culture); a tooltip when there is extra meaning the example can't carry — units, source, or the rule behind a calculated/read-only value (a computed score → explain how it is derived). Add both only when format AND meaning both need explaining.
  - Author all tooltip/placeholder text as localizable strings (resource keys), not inline literals. A form where non-obvious inputs are left without helpful guidance — or one padded with empty/generic/"e.g."-prefixed hints — is a defect, not a finished page.
- **Check the container's column count BEFORE placing fields.** The grid column count is a property of each container (its `columns` / `columnsCount`). First read the actual column count `N` of the target container, then compute placement relative to `N`: full-width field `colSpan: N` at `column: 1`; a two-column row = `column: 1` + `column: N/2 + 1`, each `colSpan: N/2`. Do not hardcode `12`/`6`/`7`, and do not place a field at a `column`/`colSpan` beyond `N` (it wraps and leaves blanks).
- **No empty layout gaps — number rows sequentially inside each container.** `layoutConfig` coordinates are LOCAL to the immediate parent container (a container you create restarts at 1). Within one container number `row` strictly `1,2,3…` with NO skipped index, counting the rows the container's existing children (the template's included) already take (a field at `row: 3` while `row: 2` is empty creates a blank gap). Never reuse global/absolute row numbers across groups, never give a field an oversized `rowSpan`, and put each field's `parentName` on its real group container.
- **An insert's `index` counts the children the parent already has — the parent template's included**, not only the inserts you emit. Read the parent's node in the `get-page` bundle before you set it; in a grid container the order in `items` follows `layoutConfig` row, then column. Worked example and several inserts into one parent: *Layout coordinates and container nesting* in `./references/page-layout-and-controls.md`.
- **Use a consistent `labelPosition` across a group — but never restyle a component to achieve it.** Use the SAME label position for all inputs within one group/panel so labels align; prefer a concrete value (`"above"`/`"left"`). However, **do NOT change a component's `appearance` (e.g. `crt.Input` `legacy`→`outline`) just to make a chosen label position render cleanly** — keeping the base Creatio look wins over the label position. If an explicit position would require an appearance change, keep the default appearance (`"auto"` is acceptable when it already renders consistently — on a record page, never on a mini page or modal, see the next rule).
- **Every field on a mini page or a modal sets `labelPosition: "above"` explicitly.** The default `auto` switches between `left` and `above` by the container's width, so a field that leaves the property out can render its label beside the input on a mini page. The only exception is a genuinely wide page — size L or XL — where `left` may be set if it reads cleanly, the same on every field of the dialog; on S/M it is always `above`. Shipped mini pages write `above` on each field and keep the component's default appearance with it — do not switch the appearance to `outline` for this. Details: *Dialogs and modals* in `./references/page-layout-and-controls.md`.
- **On a list page, extra filters go before the search, never after it.** The template's filter row (`LeftFilterContainerInner`) holds the folder actions, the filter menu and the quick filters, with `SearchFilter` last. Insert a custom quick filter or filter control into that row ahead of `SearchFilter` (read the row's children in the `get-page` bundle to set the `index`). Anything after the search field jumps while the user works with the search; `RightFilterContainer` holds the list's own tools (summaries, refresh, view switch), not filters. Details: *List (section) page layout* in `./references/page-layout-and-controls.md`.
- **Every related list is editable inline AND gets add/edit pages — both by default.** Inline adding and editing is always on: set `features.editable` on the list's `crt.DataGrid` explicitly (`enable: true`, `itemsCreation: true`), because a grid without it renders read-only rows. On top of that, wire the list's add action to a mini page and register a full page for editing — or a mini page alone when it holds the whole record. Only a tiny list (a few short columns) goes without pages, inline only. Turn inline off only when the user names that restriction, and then follow the read-only detail rule. Record the choice for each list in the plan. Details: *Grouping and page flow* in `./references/page-layout-and-controls.md`.
- **List columns fit the real data and fill the list.** On every list — a section list and a related list on a record page — check the rendered list with the demo data: no value or header is cut by an ellipsis (a money column shows the whole amount), the columns together fill the list's width instead of leaving the right part empty, and short values (date, checkbox, count) do not take width that a text column needs. A list's height follows its rows, not a fixed size. Details: *List columns* in `./references/page-layout-and-controls.md`.
- **A component beside fields aligns with them on both axes.** A timer, badge, button or value placed among fields is built like a field — caption in the label column, value in the value column — so its left edge lines up with the field values, and it sits on its own grid row with its text on the same line as the fields of that row: never pushed up against the field above, never hanging under a label. Measure it on the rendered page (text top and left edge within 2px of the neighbouring fields). Details: *Page composition* in `./references/page-layout-and-controls.md`.
- **The header shows one or two frequent actions; the rest go into one actions menu.** For every action you would put in `ActionButtonsContainer`, judge from the business scenario how often the user needs it. Keep at most two frequent ones as buttons and put the rest under one menu button (e.g. *Actions*); three or more separate header buttons need a reason named in the plan. Details: *Buttons and actions* in `./references/page-layout-and-controls.md`.
- **Never restyle components to fix a minor nuance — no scope creep.** Do not change a component's default `appearance`/style across the form (e.g. switch every `crt.Input` to `appearance: "outline"`, or change fonts/borders/colors) to work around a small issue or to satisfy another rule. That makes the whole form deviate from base Creatio — a bigger problem than the nuance it fixes. Keep platform defaults; fix only the specific field if truly needed; if a real styling change is warranted, treat it as a deliberate, scoped decision (and confirm it), not a global repaint.
- **Custom CSS is a LAST RESORT — native inputs first, then warn and confirm before applying it.** A visual-styling requirement (color, background, font/typeface, text size, spacing/padding/margin, border, width/height, alignment) is CUSTOM CSS the moment you express it as a `styles` object, a `classes`/CSS class, OR a component `extraStyles` hook (e.g. `extraStyles.toggle`, `extraStyles.label`) carrying raw CSS values such as `color`, `fill`, or `font-family` — all three carriers count equally; `extraStyles` is NOT "native" just because it is a component input. Custom CSS is not covered by the platform-upgrade compatibility guarantees that native component inputs have, so it can break or conflict on a future Creatio upgrade. The Freedom UI font is Montserrat and colors/typography come from theme tokens, so changing a font-family or hard-coding a color is custom CSS, never a native default. Mandatory order: **(1)** exhaust the component's NATIVE inputs first (resolve them with `get-component-info`; if a native property achieves the look, use it and do not mention CSS); **(2)** only if no native input can do it, tell the user plainly that no native solution exists, warn that custom CSS may break on a future platform upgrade, and ask for explicit confirmation before writing any `styles`/`classes`/`extraStyles`; **(3)** if the user declines, do not apply CSS — offer the closest native alternative or state the exact look is not achievable natively. Even a "don't ask / just apply" instruction waives the question, NOT the one-line upgrade-risk warning: never apply custom CSS silently.
- **ExpansionPanels never sit side by side — they stack vertically, full width.** A `crt.ExpansionPanel` (whether it groups inputs or wraps a detail list) always spans the FULL width of its parent tab/container. Panels are placed one under another only. Do NOT put two panels in the same row, in two columns, or inside a 2-column grid. Two-column layout applies to *fields inside* a panel, not to the panels themselves. If you have several groups/details in a tab, stack the panels vertically with a gap.
- **Match existing styles — from this page, or from a shipped reference page when this one is new.** Before adding anything, read the current page (`get-page`) and copy the conventions already in use — the ExpansionPanel style (spacing, padding, `borderRadius`, header/collapsed state), the input `labelPosition`, container spacing/padding/radius, widget sizes — so new components look identical to existing ones. Never drop a differently-styled component next to existing ones. **When the page is NEW / empty (e.g. a freshly created migration form page) so there is nothing on it to match, copy those same styles from a shipped reference page on the SAME template** (`get-page` a real Freedom page that already has ExpansionPanels / profile islands) — an ExpansionPanel or added container must look like Creatio's, not a bare default box.
- **Mind spacing between components, and make it fit the content.** Inputs in a grid: NO row spacing (rows sit tight), but keep column spacing so the two columns don't touch. Widgets / charts / metrics: use proportional row AND column spacing so they have room to breathe and align evenly — never cram them with zero gaps.
- **Keep the left and right areas proportional — the left column must not be half-empty.** The page must read as two balanced columns of comparable length, not a long content area beside a short left column. Filling the left island with just one or two fields is NOT enough when the right area is long: add a second (and if needed a third) left island with the same settings as the first and distribute key stable fields into them until the left column reaches the length of the right — at least to the end of the page's content. Fill it only with what the user needs on this page — key fields, a related-record profile, a metric that answers the page's question — and put every block through the subtract check (remove it: is anything lost?): no decorative widgets, no metric that repeats a field, no placeholder groups. If the object has nothing that passes, the page needs a template without a side profile (resolve it with `list-page-templates`), not filler. Verify this against the RENDERED page height, not the schema. See *Page composition → Balance the page* in `./references/page-layout-and-controls.md`.
- **Some fields are not finished alone — a deadline needs a timer, a Contact/Account needs a profile island, and an amount needs analytics when the user brings a question about it to the page.** Placing the field satisfies the data model, not the user: the timer and the profile island are obligatory companions on the same page, and amount analytics follows the page's question. Resolve every component/composite with `get-component-info` (never author `crt.*` names from memory) and follow *Field-driven companions* in `./references/page-layout-and-controls.md`:
  - **A money/quantity field → analytics only when it answers the page's question.** Ask what the user comes to this page to find out about the value — is the total within the limit, how much is paid and how much remains, plan against actual, the share of a larger total, the rollup across related records. When such a question exists, add the metric that answers it — a compact metric tile or gauge with an icon in its own island in the profile column (a widget is not mixed into an island of fields, unless the field explains that very metric and the plan says so), or a chart at the top of the tab that holds the data it sums up — and name the question in your plan. A metric that signals a problem (overdue, failed, over the limit) takes the attention or negative color, the others stay neutral; colors and icons follow clio's `widget-color-and-icon` guide. A dedicated Analytics tab is only for analytics that span several areas and holds enough compact charts to fill a screen. Chart sizes and rows follow clio's `dashboard-and-home-page-layout` guide (see *Analytics and metric widgets*). When none exists (a line amount on a mini page, a price the user only reads), the field stays alone. A "metric" that repeats the field's own value is never analytics.
  - **Deadline / due date / SLA date → a timer next to it.** Applies to a date the user must act before within the working horizon (SLA, task due date, next inspection, expiry) — not a far project date months away, which a metric (*days until planned end*) answers better or which needs nothing. Put a timer component beside the date (same island/group), bound to that column, so the user sees time left / overdue instead of doing date math, aligned with the fields per the rule above. The timer shows a visible caption, sets `positiveTextColor` (green) and `negativeTextColor` (red) explicitly and a `negativeTextValue` such as *Overdue*. Keep the date itself visible — the timer complements the field, it never replaces it. If the target version's catalog has no timer component, say so and offer the closest native alternative rather than hand-building a process-maintained countdown.
  - **A business-relationship Contact / Account lookup → an island with that record's profile.** Applies to a person/organization the user needs to reach (responsible, primary contact, customer, supplier, owner) — not pure audit lookups (Created by / Modified by). Add a read-only related-record profile island — name, job title, company, phone, email, communication options — captioned for the relationship (`Primary contact`, `Customer`), so the user can reach the person without leaving the page. Bind its visibility to the lookup so an unfilled record shows no blank profile.
- **Every chart answers a question named in the plan and shows all the data it compares.** A comparison chart (budget against actual, estimated against spent) carries every series it names, and each series has data on the rendered page; a chart that answers no question is removed, not kept as decoration. Chart type follows the data: shares → doughnut (up to ~6 slices), categories → bars, change over time → line.
- **Record connections are ONE `crt.Connections` element, not a ComboBox per link.** A request to show or add the record's connections ("Connected to", links to Contact/Account/Opportunity/… shown together) gets one `crt.Connections` in an expansion panel; the fields come from the object's Connections list, which is changed on the object (`update-entity-connections`), not on the page. It renders only with the `UseConnectionsComponent` feature ON — check it (a `get-entity-connections` warning naming the feature means off; without that tool in clio the state is unknown, never "on") and tell the user when it is off or could not be verified. See *Record connections* in `./references/page-layout-and-controls.md`.
- **A step-by-step page puts the stepper indicator in its own island on top by default, and the stepper in a separate island below it.** Unless the user asks for another placement, a `crt.StepperIndicator` linked to the `crt.Stepper` sits alone in a full-width island directly under the page header, the `crt.Stepper` sits in a second full-width island under it, and the navigation buttons go in the stepper's `footer` (or the page header zone, when the user wants them on top). The indicator and the buttons are placed once for the whole stepper, never copied into each step. Resolve the components with `get-component-info` and follow *Step-by-step page (stepper)* in `./references/page-layout-and-controls.md`.
- **Choose the page template BEFORE creating the page — a staged record needs the progress-bar template, not the default one.** The template is fixed at `create-page` and cannot be swapped afterwards (retrofitting means recreating the page and re-authoring its body), so derive it from the page's intended composition first. If the record is meant to show ordered process state (DCM / stage progress bar), create it from the template that already ships the progress bar instead of hand-placing a bar into the default form page. Template names are version- and environment-specific: resolve them with `list-page-templates` against the target environment and pick from what it returns — never from memory. This includes scaffolder-created section pages — `create-app-section` builds them on a default template, so create and register the record page on the right template up front rather than accepting the auto-generated one.
- **Compare the rendered page with a native Creatio page on the same template before calling it done.** Open both in the browser and run the checks in `./references/visual-check.md`: computed styles of islands, panels and groups side by side (every border, radius, shadow or background ours has and the native page lacks is a finding to remove or justify), zoomed crops of each block (a full screenshot is downscaled and loses 1px lines), and an overflow measurement. This is how defects nobody wrote a rule for get caught.

## Page creation workflow

When asked to create or redesign a page, follow this sequence:

1. **Scenario map**: write the page's one question in a sentence ("which invoices do I call about first", "is this supplier safe to order from"), then state the primary users, primary task, secondary tasks, entry points, completion signal, and whether the page is a monitor, a worklist or a report (`./references/design-judgement.md`).
2. **Page pattern**: choose one of: record page with header and tabs, profile/island layout, mini page for add/edit, dashboard/analytics page, wizard/step-by-step page, dialog/modal, or custom component — and read its pattern in `./references/page-patterns.md`. For a complex page, sketch two structurally different options and choose on written criteria (which puts the answer first, which survives the real data volume, which degrades better when fields are empty).
3. **Information architecture**: define header, primary display field, required fields, tabs, groups, profile blocks, related records, metrics, and help areas; the biggest block answers the page's question. Before authoring the page body, apply *Field-driven companions* in `./references/page-layout-and-controls.md`: timers for deadline/SLA fields, related-record profiles for business-relationship Contact/Account lookups, and analytics for money/quantity fields only where it answers the page's question, following that section's scope and fallback rules.
4. **Actions**: list top-right buttons, menu actions, inline actions, action states, confirmations, loading/progress behavior, async notifications, and cancellation/undo strategy.
5. **Fields and validation**: define field order, labels, placeholders, filters, default values, required markers, lookup/dropdown choices, read-only explanations, and copy rules.
6. **Accessibility**: verify contrast, keyboard access, accessible names, alt text, semantic roles, and error/status announcements.
7. **Acceptance checklist**: provide a concise checklist that an implementer can use before release.
8. **Render check and self-critique**: once the page is built, run `./references/visual-check.md` against a native page on the same template and answer the self-critique in `./references/review-checklists.md` in writing; fix what is weak and check again before calling the page done.

## Review output format

For audits, use this compact format:

```markdown
## Summary
[1-3 sentences]

## Audited pages
- <Page title> (`<SchemaName>`)

## Findings by page (one subsection per page; "No issues found" if clean)
### <Page title> (`<SchemaName>`)
| Severity | Category | Area | Issue | Recommendation |
|---|---|---|---|---|
| High | Accessibility (WCAG SC) / UX improvement (Nielsen H1–H10 or a rule of this skill) | ... | ... | ... |

## Recommended structure
[Proposed layout/tabs/actions]

## Accessibility checks
[Pass/risk/fix list]

## Acceptance checklist
- [ ] ...
```

Severity guidance:

- **High**: blocks user completion, hides required information, breaks accessibility, or risks destructive/irreversible action without confirmation.
- **Medium**: causes confusion, inconsistency, poor scanability, weak validation, excessive scrolling, or inefficient layout.
- **Low**: polish, copy, spacing, icon, or consistency improvement.
