# Solution Scope — Classic → Freedom UI міграція кастомізацій клієнта

Статус: **узгоджено (принципи + кейси)** · Доробок описуємо окремо, наступним кроком.

## Для кого / навіщо
- **Аудиторія:** клієнти Creatio (та їхні партнери/адміни), які роками нашаровували кастомізації на **Classic UI** у власних пакетах і переходять на **Freedom UI**.
- **Проблема:** ручний перенос layout + бізнес-логіки повільний, помилковий, невідтворюваний; клієнт не бачить, що саме він змінив відносно бази і як це лягає на Freedom.
- **Мета:** дати клієнту готове рішення — швидке, корисне, архітектурно коректне — що аналізує його Classic-конфігурацію і переносить її на Freedom UI.

## Базові принципи
1. **Один entity → по одній Freedom-сторінці на кожну роль/тип** (не «одна сторінка»): реєстр, запис, типізовані сторінки запису, міні-пейдж додавання, lookup/edit-card. Для кожної Classic-сторінки шукаємо саме її Freedom-відповідник; наявну не дублюємо.
2. **Переносимо ПОВНУ ефективну сторінку = база + усі шари клієнта разом.** Читаємо **всі шари** → зливаємо в повний ефективний вигляд → мігруємо base+customization. Дельту клієнта визначаємо лише щоб знати, **куди писати**, і щоб не загубити додане/приховане — базу під дельтою переносимо теж.
3. **Редагованість пакета визначаємо за `SysPackage.Maintainer`/lock — не за іменем чи припущеннями.**
4. **Джерело істини — пакети на стенді клієнта** (не git). На етапі аналізу — **жодних записів**; зміни лише в **редагований пакет клієнта**.
5. **Міграція рекурсивна:** деталі тягнуть власні схеми і сторінки (ролі з принципу 1 застосовуються й до деталей).

## Кейси

### A. За обсягом (scope)
- **A1. Одна одиниця:** мігруємо всі ролі сторінок цієї одиниці — **реєстр / запис / типізовані record / add-mini / lookup** — і **рекурсивно** власні сторінки її деталей.
- **A2. Пакет / застосунок цілком:** одиниця міграції включає схеми деталей + їхні сторінки в залежному порядку.
- **A3. Freedom-аналог ролі вже існує → двоетапний reconcile:**
  - **A3.1 Звірка бази (base ↔ base):** порівняти базовий Classic-вигляд із базою наявної Freedom-сторінки; зафіксувати розбіжності/прогалини бази.
  - **A3.2 Накладання дельти клієнта:** тільки після вирівнювання бази накласти кастомізації (додане / змінене / приховане).
  - Мета — привести Freedom-сторінку до **повного ефективного вигляду**, без дублів.
- **A4. Freedom-аналога ролі немає → побудувати повну Freedom-сторінку** з відповідного шаблону.

### B. Елементи кастомізації (застосовуються до ПОВНОГО ефективного вмісту)
- **B1. Поля:** усі поля/колонки, включно з кастомними колонками сутності.
- **B2. Деталі / related lists — разом із їхніми сторінками:** грід на батьківській + схема деталі + сторінка запису деталі + міні-пейдж додавання + типізовані сторінки деталі. **Рекурсивно.**
- **B3. Layout:** вкладки/групи, переміщення/вставки (`diff` insert/move/merge).
- **B4. Декларативні business rules:** BINDPARAMETER (visible/required/enabled/readonly з умовами), FILTRATION (фільтри lookup).
- **B5. Імперативна логіка:** methods, attribute dependencies, ESQ, виклики сервісів/процесів, override `onEntityInitialized`/save.
- **B6. Видалене/приховане:** елементи бази, які клієнт прибрав/сховав (з доказом зі схеми).
- **B7. Кнопки/дії:** секційні дії, run-process кнопки, друк.
- **B8. Mini-pages / lookups**, задіяні сторінкою.
- **B9. Інші компоненти:** графіки, метрики, action dashboard та інші аналітичні/дашборд-віджети.
- **B10. Кастомні (нестандартні) компоненти:** міграцію **обговорюємо з користувачем окремо**. Спершу пропонуємо максимально наближений аналог зі стандартних Freedom-компонентів; якщо не підходить — за згодою вирішуємо (кастомна реалізація / пропуск / ручне рішення). Не мігруємо наосліп.

### C. Пакети / розміщення
- **C1.** Є редагований пакет клієнта → replacing-схема туди.
- **C2.** Лише locked/product пакети → створити новий customization-пакет.
- **C3.** Багатошаровість → **реконструювати повний ефективний вигляд** із усіх шарів; редагований пакет визначаємо за `Maintainer`/lock **лише для розміщення**.
