# Merge Engine + Mapper — internals

Deterministic merge engine: N layers of a Classic ClientUnitSchema (base→top) → one **effective page** + provenance. A pure Node module, **with no Creatio/stand dependency** — tested offline against golden fixtures.

## Files (runtime — everything shipped to the client)
- `engine.mjs` — `parseSchema(src,pkg)` (**AST parsing** of the `define(...)` body via vendored `acorn`: reads the returned object literal statically, **without executing** the body — RCE-safe for stand-sourced input; anything not statically resolvable → `astDiagnostics`, fail-loud) and `mergeHierarchy(schemas)` (replay diff · merge businessRules/rules/details by key · method override stack · provenance).
- `mapper.mjs` / `designspec.mjs` / `migrate.mjs` — the mapper, the design-spec/plan renderer, and the CLI driver.

There is **deliberately no test code here**: the golden runners (`run.mjs`, `run-mapper.mjs`), their `_testkit.mjs`, and `fixtures/` live **outside the skill** — at the repo root, `engine-tests/classic-to-freedom/` — so the client-facing skill folder holds runtime only. The runners import the engine from here by relative path.

## Running the goldens
```
cd engine-tests/classic-to-freedom   # from the repo root
node run.mjs && node run-mapper.mjs  # merge + mapper, exit 1 on failure
```
(this is also what the CI job `Classic→Freedom engine goldens` does.)

## Golden result (merge — all checks green; `run.mjs` prints the live count)
- **SupportUnit** (SupportCalendar + SupportService): entity=SupportUnit; 8 fields; 3 tabs; 3 details (incl. `SupportScheduleEmployeeDetail`); 4 rules (ParentSupportUnit/SupportWorkingDayType FILTRATION, Contact/Calendar Required); method `setName`.
- **Contract** (9 layers): entity=Contract; 25 fields; 5 tabs; 14 details; 19 active rules; **removed** `State`(WorkContractsProcess), `Contact`+`ContractSumGroup`(WorkOverride); `Owner` FILTRATION + `Parent` Required (WorkContractsProcess); 71 methods.
- **F1 (order):** layers are supplied in true dependency order (`HierarchyLevel` from the stand: 299<320<…<607). `mergeHierarchy` returns `warnings` (an op hit a missing item) and `unresolvedParents` (order/seed diagnostics).
- **F2 (base seed):** `mergeHierarchy(schemas, {seedTemplate})` + the `_base/BaseModulePageV2_skeleton.js` fixture → base containers resolve (`unresolvedParents→0`), the base `ESNTab` tab appears, and the client tabs remain.

## What it proves
Reconstructing the effective page from 9 layers — which an LLM subagent previously estimated at ~142k tokens — is done here **deterministically and instantly in code**, confirming the thesis "merge = code, not LLM".

## Mapper (`mapper.mjs`, `run-mapper.mjs`)
`mapToFreedom(effective, {entityColumns})` → a Freedom ChangeSet: `viewConfigDiff` (a field = 3-part binding, control chosen by column type), `viewModelConfigDiff`/`modelConfigDiff`, `pageBusinessRules`/`entityBusinessRules` (FILTRATION→entity apply-static-filter; BINDPARAMETER→page make-* + the **inverse**), `details` (the "Expanded list" composite + dependency), `handlerStubs`, `needsDecision[]` (the judgment 20%: custom components/charts, methods, removals, unknown types).
- **container-role mapping** (lesson #6): `ProfileContainer`/`Header`→`SideAreaProfileContainer`.
- **F3 — the tab/container tree:** every field is routed by **climbing its ancestry** (`resolveOwner`): a tab ancestor→that tab (we emit `crt.Tab`+`…Grid` once, and only when the tab holds ≥1 field), Header/Profile→the side profile, otherwise→fallback+`needsDecision`. The flat "GeneralInfoTabContainer" dump is gone.
- **F9 — payload vs context (by origin):** an element is payload only if a schema layer defined it — diff-items by `templateOwned` (insert origin), keyed categories by `schemaTouched`. Base framework methods/details/components + base tabs the client merely re-arranged stay layout context (we do not synthesize a `crt.Tab` for them). `baseContextExcluded` reports what was excluded. (On the real SupportUnit: 348 methods→1, 4 details→3, 12 components→9.)
- Run: `node run-mapper.mjs` from `engine-tests/classic-to-freedom/` (together with `run.mjs` — both runners, `exit 1` on failure).
- **"Be loud" (Case check):** `unmapped-component` (the root of each dropped non-field subtree — an SLA timer, custom buttons), `referenced-module` (UI modules from `define()` dependencies outside the page unit), `field-hint` (a dynamic `hint`) — no non-standard element disappears silently; everything → `needsDecision`. See "The non-BaseModulePageV2 boundary" in the internal self-review (dev notes, outside the repo).
- For SupportUnit the code generates a ChangeSet **structurally equivalent to the slice** assembled by hand (the POC slice `body_full6.js`, outside the repo) for fields/controls/profile/detail/rules. It is **not byte-for-byte**: the base seed is supplied separately (F2 — we do not yet fetch the real parent template from the stand, hence no `Name` field), and a detail is emitted as a composite spec, not a full Expanded-list body with a toolbar. These are known gaps — see below.

## Known limitations (to finish → product)
- Symbolic enums (ENG-95412): `ViewItemType` (29), `ContentType` (7) and `DataValueType` (49) are now pinned **complete**, transcribed from core `Terrasoft.Nui/…/enums/sysenums.js`, so every member resolves to its numeric value — a schema may write `itemType` as a raw number, so the values must be exact. `BusinessRuleModule` (RuleType/Property) stays seeded as before. Lesson E1 ("never guess") is unchanged; what replaced hand-seeding is `enumDriftIssues` (engine.mjs), which diffs the pinned tables against the stand's own echo (`manifest.enumVocabulary`): a **value mismatch blocks** the gate, a member only the **stand** carries raises the non-blocking `enum-drift-advisory`, and a member only the engine carries is not a finding. A member the tables lack still surfaces per element as the `unknown-enum-member` advisory. Note the echo is produced by a clio-side `get-classic-page-sources` change that has **not shipped yet** — until it does, the guard sees nothing, the guard sees nothing on a real run. The transcription itself, however, is NO LONGER unverified: all 85 values were machine-diffed against core `sysenums.js` in a local creatio-core checkout (branch `trunk`, repo HEAD `9a6db803517`, 2026-08-19) — **ViewItemType 29/29, ContentType 7/7, DataValueType 49/49, zero value mismatches, zero members on either side only**. Two specific suspicions are settled: core genuinely has no `MONEY2` (it carries `MONEY 6`, `MONEY0 48`, `MONEY1 49`, `MONEY3 50`, and 50 is its highest value, so the table is complete to the end — the design proposal's "MONEY0–3" was loose phrasing, not a missed pin), and the `ViewItemType` 24→30 jump is real (25–29 are unused in core). The residual is version scope, not transcription: this verifies the tables against **trunk**, not against whichever platform version a given target stand runs — which is exactly what the drift guard exists to catch once the echo ships.
- Element roles / deliberate divergences (ENG-95412). The rule this engine follows: **mirror Classic's recognition; diverge only to SURFACE an element, never to hide it; record every divergence here.** Three are recorded. (1) `MENU_SEPARATOR` is the only `chrome` kind. `TIP_LABEL` carries an author caption (`getLabelCaption`, and Classic logs an ERROR when it is empty — the platform asserting the text belongs there), `TIP` generates its `tools`/`items` recursively through `generateItem`, and `GRID_LAYOUT_EDIT` is a live `Terrasoft.GridLayoutEdit` receiving `items` raw — all three carried content that `chrome` discarded with no ⚠ and no ledger trace, so they are now `UNMAPPED`/`CONTAINER`/`CONTAINER`. (2) `PROGRESS_BAR` stays `UNMAPPED` although Classic has NO dispatch branch for it (it is the one member of the 29 with no `case`, so `generateStandardItem` sends it to `default → generateModelItem` and it renders by the column's type). Mirroring would emit a silent `crt.Input`; the ⚠ instead states what Classic actually does and points at `STAGE_INDICATOR`, which is where a real classic progress bar comes from. (3) An itemType the engine cannot resolve is reported distinctly from "the schema stated none", though the runtime cannot tell them apart either — the engine is deliberately louder, because what the runtime silently swallows is exactly what a migration reader must be told. Also note `replayMerge` stubs an item on a merge whose target no lower schema defined; the runtime is a silent no-op there, so that stub is an engine-only diagnostic, not a mirror.
- Merge semantics (ENG-95412): the diff `merge` rule is key **PRESENCE**, not value — core `utils/common/json-applier.js` takes `Object.keys(config.values)` (L583-585) and assigns unconditionally (L702-705). So a later layer carrying an `itemType` key at all **overwrites** the base, including with a value this engine cannot resolve; `mergeIdentityProps` (engine.mjs) now mirrors that for `itemType`/`contentType`/`dataValueType` and warns when a resolved kind is cleared. The runtime consequence of a cleared kind is silent: `ViewGeneratorV2.generateStandardItem` routes every unrecognised itemType to `default → generateModelItem` (CrtNUI 7.8.0 L626-628), i.e. the element renders as a plain bound field. Also mirrored now: `set` (a wholesale replace — position recovered from the replaced item, every unrestated property AND every child dropped, `json-applier.js` L660-677), `remove` carrying a `properties` array (deletes only the named keys and KEEPS the element, L726-730 — the engine used to tombstone it, the one divergence in this family that HID real UI), and a `move`'s own `values` (the runtime `Ext.apply`s the move op onto the reinserted item, L283-289; ContactPageV2 really does move `SiteEventDetail` restating `values.itemType`, redundantly). Also mirrored: **per-layer group ordering** — `applyOperations` (L299-306) splits a layer's diff into buckets and runs all `merge`, then the position group, then remove-properties, then `set`; `splitDiffOps` reproduces that, so a layer doing `insert X` then `merge X` now has its merge correctly do NOTHING (array-order replay applied it and reported properties the page lacks). **`aliases`** — the table is keyed by the alias name and carries the real one (`saveAlias` L554-566), so a later op can target the element by alias; `excludeOperations` makes a whole op a no-op (L601-608, with the runtime's carve-out that a `remove` carrying `properties` is never excluded) and `excludeProperties` drops individual merge keys (L583-591); the table is singleton state across the whole fold, matching the runtime's one-reset lifetime (L793-795). And the **content properties** (`bindTo`/`caption`/`tip`/`hint`/`layout`/`generator`) now follow the same key-presence rule as the identity ones, so a layer deliberately blanking a caption or unbinding a control is applied instead of dropped.
  - **Two deliberate divergences, both recorded rather than silently taken.** `filterMoveOperation` (L313-320) drops a `move` whose name also appears in the SAME layer's removes, leaving the element removed; this engine keeps the classic reposition idiom (a move onto a tombstone RESURRECTS it) because a real page motivated it — Product's IsArchive checkbox — and neither reading can be settled without a fixture for that page. Insert ordering WITHIN the bucket (by parent-chain depth then `index`, L359/L513-545) is not reproduced; sibling order travels on the item's own `order`, and the projections promise nothing about array position. A `merge` onto an item nothing defined is also engine-only: the runtime is a silent no-op there, so the stub now carries `engineOnlyStub` and no consumer should read it as an element on the rendered page.
  - **Genuinely out of reach, not deferred by choice: `additionalDiff` and `customDiff`** (`SchemaBuilderV2.js` L104-108, L817-834). The engine is never GIVEN them — `additionalDiff` is a caller argument to the runtime's schema builder and `customDiff` belongs to a business-process element, and neither appears in any manifest key the engine reads or in any of the 5 harvested real manifests. Modelling them needs a new input from the clio side first; until then their absence can only make the engine UNDER-report a framework- or process-generated change.
  - **`remove … properties` key audit (ENG-95862 item 4).** The engine WARNS on a named key it does not model, so the
    honest question is which keys a real op may name. The harvested corpus cannot answer it — the line below records
    **zero** `remove`-with-`properties` ops in 130 bodies, and the one real occurrence known to us came from a run that
    failed (`InternalRequestHRPage` clearing `labelConfig` on a `Requester…` lookup). So the audit was done the other
    way round, inside the repo and re-checkable: enumerate every `values` key the engine **models on an item**
    (`normalizeDiffOp`) and diff it against the keys a `remove … properties` could **clear**. Two families were
    modelled-but-unclearable, which is the worst of the three states — the plan then reports a property the page no
    longer has:
    1. **`labelConfig`** — its `caption` is the control label, and the platform's own precedence is `config.caption` →
       `labelConfig.caption` → the column's title (`getLabelCaption`, ViewGeneratorV2 L1675-1689; already documented at
       `mapping-table.mjs` TIP_LABEL). Now modelled as its OWN `labelCaption` field, deliberately NOT folded into
       `caption`: folding them would leave nothing for the remove to clear, so the op would pass the membership test
       and silently change nothing — a wrong answer in place of a warning. Precedence is applied at projection time.
    2. **The handler vocabulary** (`HANDLER_PROPS` — `click`, `change`, `visible`, …), which lives in the item's
       `handlers` map rather than as a field. A removal now clears the map entry; `visible` is in BOTH vocabularies and
       clears both, since silencing the trigger while leaving the static value is a half-applied op.
    Everything else the engine models was already clearable. A key it models NEITHER way (e.g. a styling `wrapClass`)
    still warns — but at `severity: "fidelity"`, so it is an advisory the plan renders and an operator can close with
    `manifest.warningDispositions`, never a ⛔ nobody can act on. Re-run the audit by diffing the `values` keys read in
    `normalizeDiffOp` against `REMOVABLE_ITEM_PROPS` whenever either changes.
  - **Warning severity (ENG-95862).** Every `eff.warnings` entry declares `severity`: `correctness` (the op targeted an
    item no lower schema defined, or the seed is not a real fetched body — the engine's reading of the page is wrong,
    and the remedy is an act the operator can perform: fix schema order F1 / fetch the seed F2) or `fidelity` (the
    mapping is right; an effect of the op is not represented — the remedy is in this engine, so blocking on it produces
    a ⛔ nobody can clear). Five producers are correctness, three are fidelity; `computeGate` blocks on correctness only
    and **quotes each blocking warning's own hint** instead of appending one summary sentence to all eight. A warning
    with no `severity` is read as `correctness`, so a producer that forgets to declare one fails loud.
  - Measured against real data: 130 schema bodies across 5 real Classic pages contain `insert` 367, `merge` 51, `move` 7, plain `remove` 4, and **zero** `set`, `remove`-with-`properties`, `alias`, `remove`+`move` on one name, or `insert`+`merge` on one name. So the group-ordering, alias, `set` and remove-properties paths are exercised only by goldens, validated against `json-applier.js` rather than against observed pages — and the pre/post differential over that corpus reports no page changed by any of them.
- Type-name vocabulary (ENG-95412). `get-entity-schema-properties` reports clio's OWN readback names, not the engine's tokens and not always a numeric code: `EntitySchemaDesignerSupport.GetFriendlyTypeName` yields `Currency0-3` for the money subtypes, `Decimal0/1/3/4/8` for the decimals, `PhoneNumber` for 42, `RichText` for 43, `WebLink` for 44. Observed on a stand: `Contact.Phone`/`MobilePhone`/`HomePhone` = `PhoneNumber`, `Product`/`Invoice` = `Currency2`, `Invoice` = `Decimal8`. Ten of those twelve names were not keys in `mapper.mjs`, so ordinary money, decimal and phone fields raised the loud `field-control` decision claiming their TYPE was unrecognized — the engine knew the type and only not clio's spelling. `CLIO_TYPE_ALIAS` maps them onto the existing tokens through one shared `normalizeDvt`, used by BOTH the control choice and the reader-facing type label (those two diverged before on the numeric codes). Real effect: `ContactPageV2` loses its only `field-control` decision. Note a stand can also return a bare numeric code for the same column, so both forms must keep working.
- Classic field-control coverage (ENG-95412): the engine's control table is a **Freedom-side** judgement and does NOT equal Classic's own coverage — the earlier comment claiming it did was wrong in both directions. Classic RENDERS two types the engine gives no control (`MAPPING` → `generateMappingEdit`, `STAGE_INDICATOR` → `generateStageIndicator`) and THROWS `UnsupportedTypeException` for five the engine does map (`HASH_TEXT`, `SECURE_TEXT`, `IMAGELOOKUP`, `LOCALIZABLE_STRING`, `METADATA_TEXT`). Because it throws, a working classic page cannot carry such a column as a plain model item at all. `BLOB` is the correct exemplar of "Classic refuses to render it". Also note `getItemDataValueType` (CrtNUI 7.8.0 L1796-1810) gives the item's OWN `dataValueType` precedence OVER the column — an override, not a fallback — and `0` (GUID) is a legal declared value there.
- Freedom mapping (ENG-95543). The mapping knowledge is now ONE table (`mapping-table.mjs`, 53 rows): the itemType dispatch, the four hand catalogs that lived in `mapper.mjs`, and designspec's `FEATURE_TYPE`. Each row carries a **tier** — A the whole config is derivable, B the view is derivable and the imperative wiring becomes a stub, C no derivable target so a typed ⚠ with evidence. 24 rows name a `crt.*` type and every one of them is checked against the component registry (`mapping-registry.mjs`) at the OLDEST indexed version, because `latest` is a superset (205 components against 152 at 8.3.0) and validating against it green-lights a target an 8.3 stand cannot render.
  - **What the registry cannot answer, measured rather than assumed.** It has NO `required` flag on a component's own inputs (only `default`, on 795 of 1623), NO deprecation flag at component level (per-INPUT `deprecated` exists — 13 inputs at `latest` — and per-OUTPUT `deprecated` exists too — 8 outputs at `latest`, e.g. `crt.DataGrid`/`crt.ApprovalList`'s `selectedRowsChange` — and BOTH are checked, as `deprecated-input` / `deprecated-output` advisories, ENG-95863), and NO package field at all. So two sub-items of the ticket's registry section are out of reach as written: filling required props and replacing the hardcoded package knowledge (`pkg: "CrtCustomer360App"` stays hand-curated) — component-level deprecation was never real to begin with, since the registry only ever carried it per-input/per-output. The selection taxonomy (`synonyms`/`whenToUse`/`whenNotToUse`/`useCases`/`appliesToCustomEntities`/`entityCouplingNote`) exists on **8 of 205** components, so `rankCandidates` scores published taxonomy above a type-name match, states the evidence per candidate, and — since ENG-95863 — surfaces entity coupling as evidence too (never a gate: every real occurrence of `appliesToCustomEntities` is `true`, so a branch on `false` would be unreachable on real data).
  - **Deliberate divergences from the proposal's wording.** (1) HYPERLINK maps to **`crt.Link`**, not the proposed "link-styled label": `crt.Label` has no href/link input in ANY indexed version, `crt.Link` has `href`/`linkType`/`mode`/`target` from 8.3.0. (2) MENU / MENU_ITEM emit nothing of their own — a Freedom form button's dropdown IS its `menuItems` array — so they FOLD into the owning button (`crt.Menu` exists but is the compositeOnly overlay primitive, not the form idiom). (3) CONTAINER keeps its container-builder role instead of emitting a `crt.FlexContainer`: once the first-wave kinds emit, a container whose subtree produced elements is already a real container, and emitting one for a container whose whole subtree mapped to NOTHING would claim the block was migrated while its content was not. (4) MODULE stays owned by the widget / profile-card builders, which claim the ones they recognise before the generic path.
  - **An INSTANCE can fall short of its row's tier** and must not be emitted half-configured: a RADIO_GROUP with no option sub-items degrades to the typed ⚠ carrying the exact missing part, because an empty `crt.IconRadioButton` on the page is the silent-drop failure in new clothing. A `generator` on the item beats the table entirely, mirroring `generateItem`'s own precedence (the element is whatever the generator draws).
  - **Reporting invariant:** exactly ONE Layout row per emitted control. `crt.IconRadioButton` carries `values.control`, so `isField` already reports and gates it; publishing it in `tableElements` as well gave one control two Layout rows and two coverage rows. The rule is the same one the `fieldImages` fold exists for.
  - **The plan version DOES cover the registry**, through the generic `{file}`-contributes-its-CONTENT rule — a decision reversed on inspection. The earlier intent was to hash only the version identity so a CDN refresh would not invalidate approvals; but the registry changes which `registry-target` ⚠ items a plan carries, so an approval must not survive it. The version's job is "the approved plan and the built plan came from the same manifest", and a changed registry is a changed manifest. `manifest.platformVersion` alone moves the version too.
  - **Still unchecked, stated rather than implied:** `crt.*Request` / `crt.*Service` names in the reference doc (requests live in the CDN's separate RequestRegistry, published for `latest` only and not carrying all of them — `crt.HandlerChainService` is an Angular service), and the vendored index's own freshness against the CDN (it is regenerated by hand; its `meta.sources` records the SHA-256 of each registry it was built from).
- Layer order (F1): supplied in `HierarchyLevel` order from the stand (the authoritative topological depth). `SysPackageInDependency` is **not** ESQ-readable, so the raw DAG edges are unavailable — same-level ambiguity is flagged via `warnings`, not topo-sorted.
- Base seed (F2): the mechanism exists (`seedTemplate`), but the offline fixture is a skeleton; the real parent template is not yet fetched from the stand (hence no `Name`, for example).
- Functions in `attributes`/`methods` are captured by presence (provenance); their bodies are not analyzed (that is the input for the mapper / handler stubs).
