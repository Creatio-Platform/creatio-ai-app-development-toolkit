Classic→Freedom migration: the flow as it is actually built

Drawn from the code, not from the design. Four lanes, two workflows, seven executor phases — including the three the earlier diagram left out, one of which is where most of a run's time goes.

The four lanes

Two of them are Workflow scripts: deterministic control flow around agents, where every verdict is arithmetic over the engine's own numbers rather than an agent's assertion.

User

Asks, approves with a recorded plan version, picks how closely to watch, checks pages at a checkpoint, tests the result.

Migrator skill

Nine steps. Owns discovery, the engine-written plan, the three gates and the hand-over. Never improvises a build.

classic-ui-expert

Runs only when --stubs reports imperative rows. Produces behaviour cards with acceptance criteria, which re-enter the plan.

Build executor

One page per unit, three separate roles per unit, repair rounds, parking, and a machine verdict at every round.

What the earlier diagram did not show

Each of these changes how the flow is understood — where it spends time, where it can stop, and what it refuses to do.

  • ReconcileThe head of every round, not a step before the first one. It runs the CLI and refreshes the verdict — and it is the single most expensive agent in a run: 41 minutes of a measured 4h 22m. A diagram that starts the build lane at “build page” hides where the time goes.
  • PreflightA whole phase: the ⚠ Confirm worklist resolved in parallel, read-only. Its evidence is now judged and re-verified before any build, so a page whose only open row was evidence closes with no write to the stand at all.
  • RefsFetches the guidance, tool contracts and component docs once per run and cuts a per-page spec slice. Measured: 40% of everything build agents consumed was documentation re-fetched by every fresh-context unit.
  • app unitRuns before any page when the target package is missing. It owns create-app, the section on the existing object, and removing the stub — because a Freedom page on a new object migrates none of the customer's data.
  • StopsThe approval must name the plan version; an inconclusive package state, a plan gap or an unknown key each refuse the run. Re-checked on every refreshed state, not only at the head.
  • Return pathIn checkpoints and guided the run hands the page back mid-build with the acceptance criteria to exercise, and the operator's findings re-open that unit — the only signal that exists for a ported handler, which carries no verification key.
Read this as the current state, not the target. The parent branch has no PR to main yet, so none of it has shipped. Two known gaps: a surfaced lifecycle method still reads as unresolved trigger, and the flow has not yet completed a full live run end to end.
