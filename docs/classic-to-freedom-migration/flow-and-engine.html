00

The contract in one line

The engine owns the mechanical 80% — merge the chain, map to Freedom, render the plan. The agent owns the judgment 20% — feed complete inputs, resolve the worklist. Nothing is built before the plan is approved.

deterministic 80%

The engine does it. Same inputs in → same effective page, ChangeSet, and plan out. No eyeballing the schema merge.

judgment 20%

You do it. Everything mechanical it can't decide lands in needsDecision[] — the worklist you resolve.

approval-gated

Stop before build. Four readiness checks must be green, then a human approves the written plan.

03

What each stage gets right — and the agent alone gets wrong

The pipeline above (§02) shows what flows through each stage. This section is why the engine exists. Each card states the stage's rule, then contrasts two ways to do the work: ✗ agent, no engine — the coding agent reconstructing the page by reading and merging the schema layers by hand, which is where it goes wrong — versus ✓ agent + engine, the same agent running the deterministic engine, which produces the correct result.

01 · Parse — read the object, never run it

A page is a define([…], function(){ return { diff, details, businessRules } }). The engine lifts that returned object from the AST and evaluates it statically.

✗ agent, no engineevals the body — one fetched off a live stand can escape via define.constructor.constructor("return process")().
✓ agent + enginereads the body statically — nothing executes; anything unresolvable (a call, a spread) is left null and logged to astDiagnostics, never guessed.

02 · Merge — the effective page, not one layer

A Classic page is never one file. The parent template is seeded first, then the client's layers replay insert/merge/move/remove on top, base→top.

✗ agent, no enginereads the top schema's empty diff and reports “no layout / no rules”; drops an item that was removed then moved.
✓ agent + enginefolds the whole chain: a move onto a removed item resurrects it; a skeleton seed with no getActions is caught as looksSkeletal.

03 · Map — Freedom shapes, by data type

Every Classic control is routed by its ancestry and reshaped for Freedom — never copied across verbatim.

✗ agent, no enginedumps the 24-col grid as-is (it overflows); calls Activities a “Timeline”; picks the control from the Classic hint.
✓ agent + enginerebuilds the grid as 1-/2-col, routes each field to its island or tab, picks the control from the data type; a Visa → Approvals (two components).

04 · Recurse — the whole page tree

runMigration() calls itself for each related list's child edit page, each typed per-type page, and the add-record mini page — cycle-guarded, not depth-capped.

✗ agent, no enginemigrates the top page and defers “child pages later” — the miss that shipped 1 of 4 typed forms.
✓ agent + enginefolds every child / typed / mini spec in; a blocked or incomplete child bubbles up and blocks the parent — no broken child hides in a green plan.

05 · Gate & render — a blocked plan can't pass as approved

The render is gated. If any readiness check is red, renderPlan() still writes the --out file — but stamps it ⛔ do not present and exits 2, so a half-ready plan is never mistaken for an approved one. The four checks it runs → section 05.

04

What gets built, what's just context

The engine is fed the client's page plus every base template it inherits from — it needs the base to know which tab or panel each field sits in. But it must not rebuild the base parts: the Freedom template already provides them. So it tags each element by who defined it and whether a client layer touched it — which yields three outcomes, not two.

base defined it · no client layer touched ite.g. the Tabs container, the Feed tab, the Run-process action
so the engineContext. Dropped from the plan — Freedom's template already provides it; kept only to route the client's fields. fromTemplate · untouched
a client layer authored ita new field, a business rule, or a group the client inserted or moved
so the enginePayload. Becomes a real Layout / Logic row in the plan. schemaTouched · client insert
base defined it · a client layer reconfigured ita base field the client hid, moved, or re-bound
so the engineDecision. Not rebuilt, not dropped — surfaced as a base-field-override in needsDecision[], so the client's change is re-applied onto the Freedom base field, never shipped as the bare default. templateOwned + schemaTouched
Context → skip it, Freedom already provides it.
Payload → the customization the migration must carry.
Decision → a base element the client changed — re-apply, don't drop.

05

Four checks before a plan can be shown

Before the engine hands you a plan to present, it runs four checks. Fail any one and it still writes the file — but stamps it “do not present” and exits 2, so a half-ready plan can’t be mistaken for one ready to approve. The four fall into two families:

Correctness — is the merge sound?

Did the layers merge cleanly?

gate.blocked

Red until every schema was readable, the real base template was supplied (not a stand-in stub), no edit pointed at an element that doesn’t exist, and every sub-page passed this same check. In short: did the layers fold into one coherent page?

Completeness — did you give me everything?

Did you supply every part?

structure.complete

Red until every piece the plan needs is in hand: each detail’s schema, each related list’s child form, each per-type form, and the quick-add mini page. A page can merge cleanly and still be incomplete if one sub-page is missing.

Is the summary filled in?

planMetaMissing

Red while any <FILL:…> placeholder is left in the plan’s Overview or Main scope. You supply the real values in planMeta and re-run — you never type them into the file by hand.

Did you check the live app?

signalsMissing

Red until three things only the running app can answer are looked up and written down: the case stages (DCM), any connected processes, and any print reports. “Checked — found none” counts; “didn’t check” does not.

The distinction is the point: a plan can be perfectly sound yet still miss the parts, summary, or live-app answers a person needs to approve it — so completeness is three separate checks, never folded into “did it merge.”
